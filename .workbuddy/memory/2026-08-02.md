## 残留问题彻底解决（17:25，参考成功开发经验）
- 续「清理陈旧引用」后，残留 = 163 个 packed dangling（11 blob + 139 commit + 13 tree + 1 tag），`git prune` 删不动 pack 内单对象，须 `git gc`。
- **关键识别**：`fa23115` 不是一个无用孤儿对象，而是 **`v2.6.0` 版本发布 annotated tag**（tag 对象，指向 commit `b625a10c`，消息"零值兜底整改与数据准确性加固"）；它在 8/1-8/2 损坏恢复中丢失了 `refs/tags/v2.6.0` 引用才变 dangling。当前 `refs/tags/` 仅 `v1.2.0`。`b625a10c` 经 tag 可达（rev-list --all 命中），139 个 dangling commit 是与 v2.6.0 链**无关**的独立残留（损坏恢复垃圾）。
- **参考经验（先保护有用对象再清理）**：
  1. `git update-ref refs/tags/v2.6.0 fa23115d8042c825fda9820a68433375c4420dcf`（精确还原 annotated tag，避免 gc 误删发布历史）

  3. `git gc --prune=now`（GC_EXIT=0，重打包清不可达 dangling；仓库 fsck error=0 前提下安全）
- **验证**：`git fsck --full` dangling=0、error/broken/missing/invalid=0 ✅；tags = v1.2.0 + v2.6.0（v2.6.0→b625a10c）；dict 040ca668 可达；ea2734f3 经分支保护；HEAD release @ 9d618749。
- **教训**：① fsck 的 dangling 计数在 `update-ref` 后首跑可能按旧 ref 状态（疑似 ref 缓存），须 clean re-count 复核，勿凭单次数字误判「139=dangling 全等于某链」；② 清理前必须识别「丢失 ref 的 annotated tag」这类有价值对象并先恢复，而非一概 gc 删除。
