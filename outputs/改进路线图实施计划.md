## 三、短期任务（1–2 周）

### T1：建立统一 AI 提示词模板

**目标**：为所有 AI 生成代码场景提供统一、可复用的系统提示词模板，确保 `AGENTS.md` 分层约束、`lint:colors` 规则、JSDoc 模板被稳定注入。

**预期成果**：
- `prompts/system-prompt-template.md`：通用系统提示词模板。
- `prompts/component-prompt-template.md`：UI 组件生成专用模板。
- `prompts/service-prompt-template.md`：Service 生成专用模板。
- `.cursorrules` / `.trae/rules` 等 IDE 配置引用上述模板。

**验收标准**：
- 所有模板均包含 `AGENTS.md` 分层规则摘要、颜色令牌引用要求、JSDoc 模板、测试与文档要求。
- 任意开发者使用模板生成新模块时，首次输出代码的 `audit:layers` 违规率不超过 1 处。

**关键步骤**：
1. 读取 `AGENTS.md`、`src/constants/theme.tokens.ts`、`eslint.colors.config.js`，提炼必须注入的规则摘要。
2. 设计三段式模板结构：角色定义、约束清单、输出格式。
3. 分别为组件、Service、Store、类型定义编写专用模板。
4. 在 `.cursorrules`、`.trae/rules`、`.vscode/settings.json` 中引用模板路径。
5. 用 3 个真实场景（新增 Widget、新增 Service、新增类型）验证模板效果。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 模板过长导致 AI 上下文占用过高 | 生成长度受限、质量下降 | 将模板拆分为通用层 + 场景层，仅加载当前场景所需片段 |
| 模板更新后旧会话未同步 | 生成结果风格回退 | 模板文件纳入版本控制，每次修改后在项目群或站会通知全员 |

### T3：强化 Husky 预提交质量门禁

**状态**：✅ 已完成（2026-07-10）

**实际产出**：
- 重新初始化 git 仓库；创建 `.husky/pre-commit` 与 `.husky/pre-push`。
- pre-commit 扩展为 7 项检查：lint-staged（ESLint --fix + colors）→ `lint:colors` → `tsc:prod` → `audit:layers` → `audit:docs` → `verify:tokens` → `audit:tokens`。
- pre-push 运行 `test:clean` + `build`。
- `package.json` 的 `lint-staged` 更新：对 `.ts,.tsx` 运行通用 ESLint 与颜色 ESLint；对 `AGENTS.md`、`docs/*.md`、`prompts/*.md` 运行 `audit:docs`。
- `AGENTS.md` 更新至 v1.4.2。
- 回归验证：手动执行 `.husky/pre-commit` 全部 7 项通过；`audit:layers`/`audit:docs`/`audit:tokens`/`verify:tokens` 均 0 违规。

**目标**：在代码提交前强制通过分层审计与类型检查，防止违规代码进入仓库。

**预期成果**：
- `.husky/pre-commit` 脚本更新，包含 `npm run audit:layers`、`npx tsc --noEmit`、`npm run lint:colors`。
- `lint-staged` 配置仅对暂存区文件运行快速检查，避免全量扫描拖慢提交。
- 提交被阻断时的错误信息包含修复指引链接。

**验收标准**：
- 任何包含 `audit:layers` 违规或 `tsc` 错误的提交均被 Husky 阻断。
- 正常提交的平均预提交耗时不超过 90 秒。

**关键步骤**：
1. 初始化 git 仓库，安装 husky v9。
2. 编写 `.husky/pre-commit`，串行执行 7 项门禁。
3. 编写 `.husky/pre-push`，执行测试与构建。
4. 更新 `lint-staged` 配置，对不同类型文件运行对应检查。
5. 手动执行 hook 验证全部通过。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 预提交耗时过长 | 开发者绕过 Husky | 对 lint-staged 仅检查暂存文件，全量 audit 保留在 CI/pre-push 阶段 |
| 误报导致正常提交被阻 | 降低门禁信任度 | 建立白名单机制，经审批的预存基线可临时豁免；当前基线已保持 0 违规 |
| Windows 环境下 hook 路径解析异常 | hook 不被调用 | 使用 `$PWD/.husky/_/h` 绝对路径入口，避免 git bash 路径转义问题 |

### T4：建立 UI 组件迁移检查清单

**目标**：将股票池看板跨舱迁移、Widget 注册同步等架构治理型改动标准化，降低人工遗漏与返工。

**预期成果**：
- `docs/ui-migration-checklist.md`：组件跨目录/跨舱迁移的标准检查清单。
- `docs/widget-integration-checklist.md`：新增驾驶舱 Widget 的三处注册检查清单。
- 在 `AGENTS.md` 中引用上述清单，作为 AI 生成 Widget 时的默认输出。

**验收标准**：
- 任何组件迁移 PR 必须勾选清单全部 6 类引用点（路由、导航、Store、Service、组件目录、测试）。
- 新增 Widget 的 PR 必须包含 `widgetRegistry.ts`、`DEFAULT_WIDGET_CONFIG`、`WIDGET_DEFAULT_DATA_SOURCE` 三处修改。

**关键步骤**：
1. 复盘股票池看板迁移过程，枚举所有被修改的文件类型与引用关系。
2. 提炼通用迁移检查清单，覆盖页面、路由、左侧导航、Store、Service、组件目录、测试、Storybook/示例。
3. 针对 Widget 注册，制作独立的三处同步清单与代码片段模板。
4. 将清单作为 GitHub PR 模板或 Markdown 文件，要求迁移 PR 描述中勾选。
5. 在 AI 提示词中要求：任何迁移/Widget 任务，输出前先列出需修改的文件清单。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 清单过于繁琐被忽视 | 流于形式 | 将清单嵌入 PR 模板，未勾选项由代码审查者强制打回 |
| AI 仍无法按清单执行 | 生成结果遗漏 | 对 AI 输出增加“清单核对”步骤，人工逐项确认后再进入代码生成 |

**目标**：建立可复用组件的可视化示例与文档，降低后续调用与 AI 生成的理解成本。

- 示例库中组件覆盖率达到 80% 以上。

- AI 生成新页面时，能通过示例库检索到可复用组件的引用方式。

**关键步骤**：

### T6：推行三层测试策略

**目标**：建立单元测试、集成测试、E2E 测试分层体系，提升自动化测试对业务逻辑与数据流的覆盖。

**预期成果**：
- `tests/unit/`：纯函数、类型守卫、工具类测试。
- `tests/integration/`：Service + DataBridge + Store 组合测试。
- `e2e/`：关键用户旅程测试（登录 → 采集 → 分析 → 输出）。
- 更新 `vitest.config.ts`，为不同层级设置覆盖率阈值。

**验收标准**：
- 单元测试覆盖率 ≥ 80%，集成测试覆盖率 ≥ 60%，E2E 覆盖核心用户旅程。
- 新增 Service 必须附带集成测试；新增页面必须附带至少一条 E2E 路径。
- CI 中任何测试失败均阻塞合并。

**关键步骤**：
1. 按目录重构现有测试文件，建立 unit / integration 分层。
2. 编写 Service 集成测试模板，包含 `DataBridge.forward()` Mock 与 `EventBus` 清理。
3. 编写 Store 测试模板，覆盖 `withBroadcast` 跨 Tab 场景。
4. 为 5 个核心 Service 和 5 个核心 Store 补充集成测试。
5. 在 `vitest.config.ts` 中按目录配置覆盖率阈值。
6. 将覆盖率报告接入 CI，低于阈值时 PR 变红。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 集成测试 Mock 复杂度过高 | 测试脆弱、维护困难 | 封装 `createMockDataBridge()` 与 `createMockEventBus()` 工厂函数 |
| E2E 测试不稳定 | CI 频繁失败 | 优先覆盖稳定路径，对波动较大的行情数据使用 Mock 接口 |

### T7：建立文档门禁与 JSDoc 规范

**目标**：提升文档与注释的完整性、一致性与准确性，降低团队沟通成本。

**预期成果**：
- `docs/jsdoc-style-guide.md`：统一 JSDoc/TSDoc 格式规范。

**验收标准**：
- 公共导出函数 JSDoc 覆盖率达到 90% 以上。
- `audit:docs` 无参数遗漏、无过时 `@link` 引用。
- 不同会话生成的注释风格一致。

**关键步骤**：
1. 制定 JSDoc 模板，包含 `@param`、 `@returns`、 `@throws`、 `@example`、 `@see` 的使用规范。
2. 编写 `verify-docs.ts`，基于 TypeScript AST 扫描公共导出函数的注释完整性与参数匹配度。
3. 对 `src/services/`、`src/store/`、`src/core/` 进行 JSDoc 补全专项行动。
4. 将 `audit:docs` 接入 `npm run audit` 总命令。
5. 在 CI 中运行，未通过时阻断合并。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 历史代码 JSDoc 补全工作量大 | 短期拖累进度 | 分模块逐步推进，优先补齐 Service 与 Store 公共 API |
| 过度注释降低代码可读性 | 维护负担增加 | 仅要求公共 API 必须注释，私有函数可选 |

### T8：代码复杂度专项治理

**目标**：降低深层嵌套、长链式条件与重复判断，提升代码可维护性，减少 AI 修改时的回归风险。

**预期成果**：
- `scripts/complexity-scan.ts`：基于 AST 扫描嵌套深度、分支链长度、重复条件。
- `optimization-plan.md` 中 P0 模块完成重构。
- 复杂度指标下降：真实深层嵌套减少 ≥ 50%，≥6 分支链减少 ≥ 60%，重复条件减少 ≥ 40%。

**验收标准**：
- `npm run complexity-scan` 输出中，P0 模块无 ≥6 层嵌套、无 ≥8 分支链。
- 重构后 `audit:layers`、`tsc:prod`、单元测试全部通过。

**关键步骤**：
1. 基于现有 `nested-code-review-report.json`，按模块排序形成治理清单。
2. 对 `src/core/databridge.ts`、`src/core/databridgeHandlers.ts`、`src/mcp/core/server.ts`、`src/mcp/core/client.ts`、`src/data/db-migrations.ts`、`src/data/sectorDefinitions.ts` 等 P0 模块逐个重构。
3. 应用策略表、卫语句、提前返回、谓词函数提取等手法降低复杂度。
4. 每重构一个模块，运行对应单元测试与 `tsc:prod`。
5. 将 `complexity-scan` 接入 CI，作为趋势监控。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 重构引入行为变更 | 业务逻辑回归 | 重构前为每个 P0 模块补充快照测试或集成测试，重构后比对输出 |
| 复杂度指标下降但可读性未改善 | 形式主义 | 将重构结果提交人工评审，重点审查是否真正降低认知负担 |

## 五、长期任务（3–6 个月）

### T9：构建项目专属 AI 记忆层（RAG）

**目标**：将 `AGENTS.md`、设计令牌映射、知识卡片、测试模板、迁移检查清单等知识资产向量化，提升 AI 长会话稳定性与生成质量。

**预期成果**：
- `ai-knowledge/` 目录：存放结构化知识片段。
- 本地向量存储或轻量级 RAG 服务（如使用 `langchain` + `chroma` 或项目内 Markdown 索引）。
- AI 会话启动时自动加载与当前任务相关的知识片段。

**验收标准**：
- RAG 检索准确率 ≥ 80%（对 20 个典型查询，前 3 条结果包含正确答案）。
- 使用 RAG 后，AI 生成代码的 `audit:layers` 首次违规率下降 50%。

**关键步骤**：
1. 梳理需要纳入 RAG 的知识资产清单。
2. 将长文档按主题切片（每片 500–1000 字），维护元数据（主题、关键词、版本）。
3. 选择 RAG 方案：本地 Chroma 向量库、项目内 SQLite 索引，或 WorkBuddy 内置知识库。
4. 开发索引与检索脚本，支持按任务类型（组件/Service/测试/迁移）加载相关知识。
5. 在 AI 提示词工程工具（Cursor/Trae/WorkBuddy）中配置知识库引用。
6. 持续收集 bad case，迭代切片策略与检索算法。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 知识片段过多导致检索噪音大 | AI 被无关信息干扰 | 引入元数据过滤，仅加载与当前文件层、当前任务类型相关的片段 |
| 向量库依赖外部服务 | 离线环境不可用 | 优先选择本地向量库方案，确保无外网时仍可工作 |

---

### T10：引入视觉回归测试

**目标**：量化设计稿与代码渲染差异，防止 UI 改动引发 unintended visual changes。

**预期成果**：
- Playwright 视觉回归测试覆盖驾驶舱、分析舱、交易舱、输入舱核心页面。
- 基线截图纳入版本控制或独立存储。
- PR 中自动生成视觉差异报告。

**验收标准**：
- 核心页面视觉回归测试通过率 ≥ 95%。
- 任何导致像素级差异的 UI 改动必须在 PR 中可见并经过审批。

**关键步骤**：
1. 在 Playwright 配置中启用 `screenshots` 与 `toHaveScreenshot` API。
2. 为每个核心页面编写稳定的视觉回归测试用例，固定 viewport 与主题状态。
3. 建立基线截图库，标注每个基线对应的 commit。
4. 在 CI 中运行视觉回归测试，生成差异报告。
5. 制定视觉差异审批流程，明确可接受的差异阈值。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 动态数据导致截图不稳定 | 误报率高 | 对行情数据、时间等动态元素使用 Mock 或隐藏处理 |
| 基线截图库体积过大 | 仓库膨胀 | 将基线截图存储在独立 LFS 或对象存储中 |

---

### T11：建立 AI 生成—审计—修正飞轮

**目标**：实现 AI 生成代码、自动审计、反馈修正的闭环，使生成质量随项目演进持续提升。

**预期成果**：
- 自动化脚本：接收 AI 生成代码 → 运行 `audit:layers` / `tsc:prod` / `lint:colors` → 将错误注入 AI 上下文 → 输出修正版本。
- 修正历史记录：保存常见错误模式与修复方案，供 RAG 使用。
- 人工确认机制：修正后的代码仍需人工审批方可写入仓库。

**验收标准**：
- 80% 的常见分层违规可通过一次自动反馈循环修复。
- 飞轮处理单文件平均耗时不超过 3 分钟。

**关键步骤**：
1. 开发 `ai-codegen-feedback.ts` 脚本，封装审计命令与错误解析。
2. 将错误信息转换为 AI 可理解的“修正提示”，按错误类型分类。
3. 建立错误—修复模式库，记录高频问题（如 lib 被业务污染、硬编码颜色）。
4. 集成到 WorkBuddy / Cursor / Trae 的 Agent 工作流中。
5. 设置人工确认 gate，避免自动修正引入语义错误。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 自动修正过度“修复”导致语义错误 | 引入隐蔽 bug | 强制人工 diff 确认，关键文件需代码审查 |
| 飞轮循环陷入死循环 | 资源浪费 | 设置最大迭代次数（如 3 次），超时转人工 |

### T12：建立架构健康度仪表盘

**目标**：持续监控分层违规、硬编码、嵌套深度、测试覆盖率、文档同步率等核心指标，形成可视化治理看板。

**预期成果**：
- `scripts/health-dashboard.ts`：聚合各门禁与扫描结果，生成 JSON/MD 报告。
- 可选 Web 看板：在开发服务器中展示实时指标。
- 每周自动输出架构健康报告。

**验收标准**：
- 仪表盘覆盖 ≥ 8 项核心指标。
- 指标趋势可追踪，历史数据保存 ≥ 90 天。
- 任一指标恶化时，自动通知相关负责人。

**关键步骤**：
1. 定义核心指标：layers 违规数、hardcode 数量、嵌套深度 ≥4 处数、链式条件 ≥6 处数、测试覆盖率、JSDoc 覆盖率、文档同步率、路由 orphan 数。
2. 开发聚合脚本，复用现有 `audit:*`、`complexity-scan`、`verify-docs` 输出。
3. 将结果输出为 `health-report.json` 与 `health-report.md`。
4. 可选：使用轻量级图表库搭建 Web 看板。
5. 配置定时任务（如每周一早上）自动发送报告。

**风险与缓解措施**：
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 指标过多导致注意力分散 | 关键问题被淹没 | 每期报告仅突出 Top 3 恶化指标与 Top 3 改进指标 |
| 数据采集脚本运行耗时过长 | 看板更新不及时 | 对可增量计算的指标使用缓存，仅重新计算变更部分 |
