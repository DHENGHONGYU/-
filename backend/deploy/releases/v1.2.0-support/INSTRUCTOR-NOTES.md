## Slide 3: 指纹技术原理 (8 min) ⭐ 核心

### 演讲要点

#### 3.1 什么是向量指纹 (2 min)

- 用一句话解释: "指纹就是 Embedding 服务返回向量的'DNA', 取前 8 个浮点数做 SHA256, 取前 16 位."
- 展示算法代码, 逐行解释:
  - `head=8`: 取前 8 个 float
  - `struct.pack(">f", ...)`: 大端序打包 (强调"大端"是为了跨平台一致)
  - `hashlib.sha256(...).hexdigest()[:16]`: SHA256 取前 16 个 hex 字符
- 关键点: "这个算法零依赖, 只用 Python 标准库, 任何环境都能跑."

#### 3.2 为什么取前 8 个浮点数 (2 min)

- 展示对比表, 重点讲"平衡点"概念.
- 前 1 个: 太少, 容易碰撞 (不同向量可能前 1 个 float 相同).
- 全 384 维: 太慢, 网络传输 + 哈希开销大.
- 前 8 个: 96 字节, 哈希 <1ms, 区分度足够.
- 强调: "我们在 float32→float16 精度丢失、模型切换、代码改写等场景下做了大量测试, 前 8 个 float 能稳定触发漂移."

#### 3.3 4 层断言架构 (3 min)

- 逐层讲解 ASCII 架构图:
  - **Check 1 元数据** (硬阻断): model_id / dim / max_batch / loaded — 从 /api/embed/config 获取
  - **Check 2 指纹** (硬阻断): SHA256[:16] 比对 — 核心! 从 /api/embed/embed 获取向量后计算
  - **Check 3 维度** (硬阻断): 3 vectors x 384 dim — 检查每条向量维度
  - **Check 4 运行时** (非阻塞): slow_threshold_ms / uvicorn_workers — 只告警不阻断
- 强调"硬阻断"和"非阻塞"的区别: "Check 1/2/3 任一失败, 脚本 exit 1, CI/CD 阻断发布. Check 4 只打 [WARN]."

#### 3.4 为什么有效 (1 min)

- 核心原理: "确定性模型对相同输入产生相同输出. all-MiniLM-L6-v2 没有 dropout, 给定相同文本, 输出向量逐位一致."
- 提醒: "如果未来引入带 dropout 的模型, 需要额外关闭随机性或采用统计指纹方案."

### 互动建议

## Slide 4: 指纹漂移的 4 种类型 (7 min)

### 演讲要点

#### 4.1 漂移分类全景 (1 min)

- 展示 4 种类型全景图, 快速过一遍名称: 模型切换 / 维度漂移 / 精度丢失 / 代码变更.
- 强调严重级别: Type 1/2 是 P0 致命, Type 3 是 P1 严重, Type 4 是 P2 中等.

#### 4.2 各类型详解 (4 min)

- **Type 1 模型切换**: 根因是部署时误用其他模型或 HF_HOME 被覆盖. Check 1 + Check 2 双重捕获, 最容易识别. 强调"model_id 字段直接暴露".
- **Type 2 维度漂移**: 根因是调试代码泄漏 (开发者临时追加 metadata float 忘记删). Check 3 单层捕获. 特征是 dim=385 (调试) 或 dim=0 (异常).
- **Type 3 精度丢失**: 根因是 FP16 量化未走评审. Check 2 单层捕获. 强调"最隐蔽" — model_id 和 dim 都正确, 仅指纹变化. 严重级别 P1, "召回率下降但不会归零, 难以被业务监控及时发现".
- **Type 4 代码变更**: 根因是推理代码改写 (normalize 顺序、padding 策略). Check 2 单层捕获. P2 中等, "需结合代码 diff 判断是否预期".

#### 4.3 检测覆盖矩阵 (2 min)

- 展示矩阵表, 强调: "Check 2 是'万能捕获层', 4 种类型它都能抓到. 但单靠 Check 2 无法区分 Type 3 和 Type 4, 需结合代码 diff 判断."
- 让学员拍照保存这个矩阵, "以后遇到 Check 2 FAIL, 看这张表就知道可能是哪种类型".

### 互动建议

- 提问: "Type 3 精度丢失为什么严重级别是 P1 而不是 P0?" (答案: 召回率下降但不归零, 业务监控不易发现, 但不会立即导致服务不可用)
- 提问: "Check 2 能检测到 Type 2 维度漂移吗?" (答案: 能, 因为维度变化导致前 8 个 float 值不同, 但 Check 3 更直接)

## Slide 5: 指纹漂移识别方法 (6 min)

### 演讲要点

#### 5.1 退出码速查 (1 min)

- 快速过退出码表: 0=通过, 1=漂移, 2=不可达.
- 强调: "exit 2 不是漂移, 是服务没跑起来. 别搞混了."

#### 5.2 Check 2 失败消息格式 (1 min)

- 展示失败消息格式, 解释两个字段:
  - `当前=`: 当前服务返回向量算出的指纹
  - `基线=`: --baseline 参数或 ConfigMap 中记录的 v1.1.0 基线
- "看到这条消息, 第一件事不是回滚, 而是搞清楚'当前'和'基线'哪个是对的."

#### 5.3 双机对比法 (2 min)

- 这是本页的核心! 讲解"10 秒定位"方法.
- 场景: 回滚后 Check 2 仍然 FAIL, 需要判断是"基线错了"还是"真的还在漂移".
- 操作: 在基线机器和当前机器上分别跑一条 python 单行命令, 对比 v[i][:4].
- 展示命令, 告诉学员"这条命令我待会会发到群里, 大家保存下来."

#### 5.4 决策树 (2 min)

- 展示决策树, 讲解两种分支:
  - v[i][:4] 相同 + 指纹不同 → 基线版本抄错了 → 重新 --gen-baseline
  - v[i][:4] 不同 → 真实漂移 → 执行回滚或联系开发
- 强调: "这个决策树是 Slide 8 FAQ-P1 实战的核心逻辑, 务必记住'先比 v[i][:4], 再下结论'."

## Slide 6: 回滚决策流程树 (10 min) ⭐ 核心

### 演讲要点

#### 6.1 完整回滚决策流程 (7 min)

- 逐 Step 讲解决策树, 这是全场最重要的内容:

- **触发条件** (1 min): T1 (P95 延迟 >500ms 持续 5 分钟) + T2 (下游业务方提工单) + T3 (发布经理审批). "满足 T2 + T3 即可启动回滚, T1 是辅助信号."

- **Step 1: 取证据** (2 min): 重点强调"禁止盲目回滚!"
  - 4 个动作: ① kubectl logs 取日志 ② 记录哪个 Check FAIL、退出码、当前指纹、基线指纹 ③ 跑双机对比 ④ 截图保存
  - "取证据只需 10 秒 (一条 kubectl logs), 但能避免 30 分钟的无效回滚."

- **Step 2: 证据分类** (1 min): 根据 Check 1/2/3 哪个失败, 分类到 Type 1/2/3/4.

- **Step 3: 执行回滚** (1.5 min): kubectl rollout undo → rollout status → 等待 Pod Running. "约 3 分钟."

- **Step 4: 验证回滚结果** (1.5 min): helm upgrade 重新部署验证 Job → wait → logs. "exit=0 关闭工单, exit=1 进 Slide 8 FAQ-P1 排查."

#### 6.2 核心原则 (3 min)

- 展示错误做法 vs 正确做法对比图.
- 错误做法: "收到工单 → 直接 rollout undo → 跑验证 → 发现还是 FAIL → 不知道回滚到哪."
- 正确做法: "收到工单 → ① 取 Job 日志 → ② 分类证据 → ③ 记录基线/当前 → ④ 再决定回滚 → ⑤ 回滚后验证."
- 讲解为什么不能盲目回滚:
  - 基线抄错 → 回滚毫无意义, 反而中断正常服务
  - 调试代码泄漏 → 回滚可能有效, 但根因没解决, 下次还会犯
- 让学员把"先取证据, 再做决策"默念 3 遍.

## Slide 7: 回滚触发条件 & 评估标准 (5 min)

### 演讲要点

#### 7.1 三条红线 (2 min)

- 🔴 **硬红线**: Check 1/2/3 任一 FAIL, 无需审批, 验证脚本 exit=1 即触发. "机器说了算."
- 🟡 **软红线**: CPU/内存 +20% 持续 10 分钟, 需 SRE 确认非流量峰值. "人说了算, 15 分钟响应."
- 🟠 **业务红线**: 下游 API 错误率 >1% + 发布经理审批. "30 分钟响应."
- 强调: "硬红线是自动化的, --fail-fast 只覆盖硬红线场景."

#### 7.2 评估矩阵 (2 min)

- 逐行讲解评估矩阵: Check 失败 → 漂移类型 → 严重级别 → 是否回滚 → 回滚目标 → 回滚后动作.
- 特别注意: Check 4 (运行时) 不回滚, 服务不可达 (exit=2) 也不回滚 (先修服务).
- "exit=2 不是漂移, 是服务挂了, 回滚没用, 先把服务弄起来."

#### 7.3 审批权限 (1 min)

- 快速过审批权限表: 硬红线无需审批, 软红线 SRE oncall 15 分钟, 业务红线发布经理 30 分钟.

### 互动建议

- 提问: "如果 Check 4 (运行时参数) FAIL 了, 要不要回滚?" (答案: 不回滚, Check 4 是非阻塞的, 只需调整参数)

## Slide 8: FAQ-P1 实战: Check 2 指纹漂移排查 (8 min) ⭐

### 演讲要点

#### 8.1 场景 (1 min)

- 朗读场景: "回滚 v1.2.0 → v1.1.0 后, 重新跑验证脚本, Check 2 FAIL: 指纹漂移!"
- 提出核心问题: "回滚了为什么还漂移? 是回滚没生效, 还是基线错了?"
- "这个场景占生产事故的 60% 以上."

#### 8.2 Step 1: 10 秒取证据 (3 min)

- 展示一条 python 单行命令, 在基线机器和当前机器上分别执行.
- 展示输出对比示例: 基线机器 v[0][:4] 和当前机器 v[0][:4] 是否相同.
- "10 秒, 一条命令, 就能判断是基线错了还是真的还在漂移."

#### 8.3 Step 2: 三类根因判定表 (2 min)

- 逐行讲解:
  - v[i][:4] 相同 + 指纹不同 → 基线版本抄错了 (P3) → 重新 --gen-baseline
  - v[i][:4] 不同 → 真实模型切换 (P0) → 检查 --to-revision
  - 指纹相同但 Check 2 FAIL → 比对的基线版本号不对 (P2) → 核对 --baseline 参数

#### 8.4 判定流程图 (1 min)

- 展示流程图, 与 Slide 5.4 决策树呼应.

#### 8.5 常见误判 (1 min)

- 讲解 3 个常见误判:
  - "回滚失败了, 再回滚一次" → 其实是基线抄错
  - "脚本有 bug" → 其实是基线与版本不匹配
  - "服务没回滚" → 其实是 rollout undo 回到了上一个坏版本
- 强调: "v[i][:4] 相同 = 基线错了, 不是服务错了."

## Slide 9: FAQ-P2/P3 实战: 元数据 & 维度漂移 (7 min)

### 演讲要点

#### 9.1 FAQ-P2: Check 1 FAIL (3 min)

- 展示现象: "model_id mismatch: got=paraphrase-MiniLM-L6-v2, expected=all-MiniLM-L6-v2"
- 根因: HF_HOME 环境变量被覆盖, 加载了缓存中的其他模型.
- 排查 3 步: ① 检查 Pod env ② 检查 Deployment env ③ 检查 /api/embed/config
- 修复: kubectl set env 修正 HF_HOME → rollout status → 重新验证.

#### 9.2 FAQ-P3: Check 3 FAIL (3 min)

- **现象 A (dim=0)**: 服务启动异常, 模型未加载完. 修复: 检查 health, 重启 Pod.
- **现象 B (dim=385)**: 调试代码泄漏. 排查: ① 检查镜像 tag ② 检查 deploy.sh 版本 ③ grep 代码中 append/concat/pad. 修复: 回滚或修正 deploy.sh.

#### 9.3 P2/P3 对比总结 (1 min)

- 快速对比: P2 是 model_id 问题 (HF_HOME), P3 是 dim 问题 (调试代码/版本不匹配).
- "P2 和 P3 都是'配置/部署错误'而非'模型本身问题', 修复后无需重新训练或调整模型."

## Slide 11: CI/CD 门禁集成 (5 min)

### 演讲要点

#### 11.1-11.2 工作流与 5 个 Job (3 min)

- 展示 5 个 Job 的流水线图, 讲解依赖关系:

### 常见学员问题及标准回答

| 学员问题 | 标准回答 |
|---------|---------|
| "如果 Embedding 服务没有 /api/embed/config 端点怎么办?" | 指纹验证脚本会跳过 Check 1, 仅做 Check 2/3/4. 建议联系开发团队补上 config 端点. |
| "基线 SHA 能用 v1.0.0 的吗?" | 不能. 基线必须与当前部署版本匹配. v1.2.0 回滚到 v1.1.0, 基线必须是 v1.1.0 的. |
| "CI/CD 门禁能跳过吗?" | 硬红线不能跳过. 如需紧急发布, 需发布经理审批后在 workflow_dispatch 中手动触发并记录原因. |
| "如果向量是浮点数, 不同机器计算结果会不会不同?" | all-MiniLM-L6-v2 是确定性模型, 相同输入相同输出. 但如果涉及 GPU 推理, 不同 GPU 型号可能有微小差异, 建议固定推理设备. |
| "CronJob 巡检会占用多少资源?" | 每次 <500m CPU + 256Mi 内存, 运行时间 <5 秒. 对 Embedding 服务仅发 3 个 HTTP 请求, 几乎无负载. |
