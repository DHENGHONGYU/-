# V9 数据架构修订建议

> **基于文档**：`v9-system-blueprint.md` vs `V9核心数据字典与类型定义（整合版）.md`（P0级）
> **修订目标**：使系统蓝图的五层架构、数据架构与实际 P0 核心数据定义保持一致
> **修订级别**：P0 — 核心架构对齐，建议优先纳入下一版蓝图迭代

---

## 一、总体差异概览

| 维度 | 蓝图现状 | P0 数据字典现状 | 差异级别 | 影响范围 |
|------|----------|-----------------|----------|----------|
| L2 数据层职责描述 | 仅列 3 个文件（db.ts/dataLayer.ts/types.ts） | 涵盖 6 大核心业务实体 + 7 大核心评分实体 + 4 类基础数据结构 | 高 | 架构认知、新人上手 |
| L3 引擎层职责描述 | 仅列服务目录名 | 对应 7 个 P0 评分/策略实体的产出，含双策略编排 | 高 | 模块边界、数据流向 |
| IndexedDB Store 数量 | 17 个 | 至少缺少 2 个 P0 级 Store（hot_sector_scores、value_pit_scores） | 高 | 数据库 Schema 设计 |
| 数据流引擎归属 | 置于 L3 引擎层（core/dataflow/） | P0-5 数据流基础定义在 src/core/dataflow/，与 L1 的 core/ 路径重叠 | 中 | 层次划分一致性 |
| 通信协议枚举完整性 | EnvelopeTarget 仅示例 'indexeddb' | P0 定义 8 种 EnvelopeTarget、11 种 ModuleId、30+ 种 EnvelopeAction | 中 | 协议文档完备性 |
| 事件总线与数据流关系 | 独立描述 6 个事件 | P0-5 定义 12 个 DataChannel，两套体系关系未说明 | 中 | 数据流规范统一 |

## 二、五层架构修订建议

### 2.1 数据层（L2）职责补全

**问题**：蓝图中 L2 数据层仅列 `db.ts | dataLayer.ts | types.ts` 三个文件名，未体现数据层的核心职责与承载的实体规模。P0 数据字典显示数据层承载了系统最核心的 28 个 P0 实体中的 **17 个**（业务实体 + 评分实体 + 基础数据结构），是系统的"数据中枢"。

**修订建议**：

将 L2 数据层描述从文件罗列升级为**职责 + 实体分类**的完整表述：

```
L2 数据层：data/
  职责：数据持久化、数据访问抽象、数据版本管理、数据质量标记
  核心文件：
    db.ts              — IndexedDB 连接与 Schema 定义（19 个 Store）
    dataLayer.ts       — 数据访问层（Data Access Layer），统一 CRUD 接口
    types.ts           — 核心类型定义（28 个 P0 实体中的 17 个）
  承载实体（P0 级）：
    业务实体（6）：Stock / Order / Signal / Watchlist / Portfolio / PortfolioHolding
    评分实体（7）：V6Score / HotSectorScore / ValuePitScore / DualStrategyResult
                  / RotationSignal / HotSectorDimensionScores / ValuePitDimensionScores
    基础结构（4）：KlineBar / DailyQuotes / DataLayerResult<T> / SignalSnapshot
  对外协议：DataLayerResult<T> — 所有数据操作的标准返回格式
```

### 2.2 引擎层（L3）职责补全与数据流引擎归属修正

**问题 1 — 职责描述不足**：蓝图中 L3 引擎层仅列服务目录名（scoring/fetcher/trading/input），未说明各子模块对应的核心产出实体。P0 数据字典中 **7 个核心评分实体**全部由引擎层产出，是系统的"计算中枢"。

**问题 2 — 数据流引擎归属矛盾**：蓝图将 `core/dataflow/（数据流引擎）` 置于 L3 引擎层，但：
- 路径前缀 `core/` 在架构图中属于 L1 基础设施层
- P0-5 数据流基础（DataChannel / DataPacket / ChannelMeta）定义文件为 `src/core/dataflow/dataflowTypes.ts`，与 L1 的 `core/` 路径一致
- 数据流引擎本质是基础设施（类似 eventBus），而非业务引擎

**修订建议**：

1. **将 core/dataflow/ 从 L3 移至 L1**，与 `core/` 路径归属保持一致：

```
L1 基础设施层：lib/, config/, core/
  eventBus | DataBridge | ACL | Envelope | theme | routes
  + dataflow/ — 数据流引擎（DataChannel / DataPacket / ChannelMeta）
```

2. **补全 L3 引擎层的产出实体映射**：

```
L3 引擎层：services/（agents/ 初始实现）
  子模块 → 核心产出（P0 实体）：
    scoring/     — 评分引擎 → V6Score / IndustryScore（P1）
    fetcher/     — 数据采集 → Stock / DailyQuotes（写入 L2）
    trading/     — 交易引擎 → Order / Signal
    strategy/    — 策略引擎 → HotSectorScore / ValuePitScore / DualStrategyResult
                    / RotationSignal
    rotation/    — 轮动引擎 → RotationSignal / RotationSectorScore（P1）
    input/       — 输入服务 → Stock（池管理）/ Watchlist
  说明：引擎层通过 DataBridge / Envelope 协议向 L2 写入数据，
        通过事件总线向 L4 应用层推送结果
```

### 2.3 L1 基础设施层补充

**问题**：蓝图 L1 列出了 Envelope，但 P0-1 基础通信协议包含 5 个实体（StandardEnvelope / EnvelopeMeta / ModuleId / EnvelopeAction / EnvelopeTarget），是一个完整的协议体系，不应仅以 "Envelope" 一笔带过。

**修订建议**：

```
L1 基础设施层：lib/, config/, core/
  通信协议：StandardEnvelope / EnvelopeMeta / ModuleId / EnvelopeAction / EnvelopeTarget
  数据基础设施：eventBus | DataBridge | ACL | dataflow/
  UI 基础设施：theme | routes
```

## 四、数据交互协议修订建议

### 4.1 StandardEnvelope 协议描述补全

**问题**：蓝图中 StandardEnvelope 的 `target` 字段仅示例 `'indexeddb'`，但 P0 数据字典定义了 **8 种 EnvelopeTarget**，且蓝图未说明来源文件与完整枚举。

**修订建议**：在蓝图的标准信封定义中补充完整枚举说明：

```ts
interface StandardEnvelope {
  meta: {
    source: ModuleId;        // 11 种枚举：fetcher / stockpool / analyzer / tradinghub /
                             //          system / user / rotation / sector / news / trading / strategy
    target: EnvelopeTarget;  // 8 种枚举，不仅限于 'indexeddb' / 'db'
    action: EnvelopeAction;  // 30+ 种动作，分 5 大类：
                             //   股票数据操作（4）、评分数据操作（8）、
                             //   交易与信号（4）、策略触发（3）、系统与其他（10+）
    traceId: string;
    timestamp: number;
    dataVersion: number;
  };
  payload: unknown;
}
```

同时建议增加来源说明：
- **定义位置**：`src/core/envelope.ts`（工厂与校验）、`src/config/dbConfig.ts`（枚举常量）
- **关联矩阵**：ModuleId × EnvelopeAction × EnvelopeTarget 构成完整的 ACL 权限控制矩阵

### 4.2 调用方向矩阵补充 Module 映射

**问题**：蓝图的调用方向矩阵基于 5 层架构，但 P0 定义了 11 个功能模块（ModuleId）。11 个模块如何归入 5 层，蓝图未明确说明，导致 ACL 矩阵与调用规范之间存在断层。

**修订建议**：在调用方向矩阵前增加 **模块-层级映射表**：

| 层级 | 包含的 ModuleId | 说明 |
|------|----------------|------|
| L5 展示层 | `user` | 前端用户操作 |
| L4 应用层 | —（应用舱室无独立 ModuleId） | 五舱作为应用编排层，不直接发送 Envelope |
| L3 引擎层 | `fetcher`, `stockpool`, `analyzer`, `tradinghub`, `trading`, `rotation`, `sector`, `news`, `strategy` | 9 个业务引擎模块 |
| L2 数据层 | —（数据层被动接收） | 通过 DataBridge 接收 Envelope，不主动发起 |
| L1 基础设施层 | `system` | 系统级操作，拥有最高权限 |

### 4.3 事件总线与 DataChannel 的关系澄清

**问题**：蓝图描述了两套数据通信体系：
1. **Envelope + DataBridge**：面向数据持久化的请求-响应模式
2. **事件总线（EventBus）**：面向模块解耦的发布-订阅模式

而 P0-5 数据流基础又定义了 **12 个 DataChannel**，构成第三套通信体系。三者的关系、适用场景、何时使用哪一套，蓝图未说明。

**修订建议**：在"数据交互协议"章节增加 **通信体系定位说明**：

| 通信机制 | 定位 | 典型场景 | 数据载体 |
|----------|------|----------|----------|
| Envelope + DataBridge | 数据层写入协议 | 引擎层向 IndexedDB 写入数据 | StandardEnvelope（P0-1） |
| EventBus（事件总线） | 模块间通知 | 数据变更通知（如 scores:changed） | 事件名 + 轻量 payload |
| DataChannel（数据流） | 实时数据流 | 行情推送、信号推送、状态监控 | DataPacket<T>（P0-5） |

**建议原则**：
- 跨层数据写入 → 使用 Envelope + DataBridge（有 ACL 校验）
- 同层或跨层状态通知 → 使用 EventBus（轻量发布订阅）
- 高频实时数据流 → 使用 DataChannel（有通道元数据、顺序保证）

## 五、模块间桥梁补全

**问题**：蓝图的"模块间桥梁"列出了 5 座桥梁，但 P0 数据字典中定义的 11 个 ModuleId 涉及更多数据流路径，尤其是策略引擎、轮动模块、板块模块、资讯模块的桥梁完全缺失。

**修订建议**：补充以下桥梁：

| 桥梁 | 起点 | 终点 | 数据 | 触发 | 文件 |
|------|------|------|------|------|------|
| 策略计算桥 | `strategyEngine` | `db.ts` | HotSectorScore / ValuePitScore | 定时/手动触发 | `src/services/strategy/*` |

## 六、核心字段补全建议

**问题**：蓝图"核心字段"表列出了 7 个字段，但 P0 核心实体中还有大量高频出现的关键字段未被收录。

**修订建议**：补充以下 P0 级核心字段：
