# 网页测试检索校对是否纳入数据采集改进方案——比对分析与建议

> **结论先行**：不建议将“网页测试/检索/校对”能力（当前实现为 `hybrid-proofread` 代码安全校对模块）直接纳入本轮数据采集改进方案。两者属于不同业务域，目标、输入输出、运行时环境、用户画像均不同。更合理的做法是：本轮聚焦金融数据采集链路；`hybrid-proofread` 作为独立的“代码安全/项目健康”子项，复用本轮沉淀出的**配置注册表、流水线 Trace、任务调度、持久化**等基础设施，但保持业务边界清晰。

---

## 一、所指对象界定

用户提到的“网页测试检索校对”在仓库中对应实现为 **`src/services/hybrid-proofread`** 及其配套文件：

| 文件 | 作用 |
|------|------|
| `src/services/hybrid-proofread/index.ts` | 编排完整校对流程：`规则同步 → 本地扫描 → 规则评估 → 云端风险检查 → 生成报告` |
| `src/services/hybrid-proofread/localCollector.ts` | 遍历本地项目路径，计算文件哈希 |
| `src/services/hybrid-proofread/ruleEngine.ts` | 基于正则规则检测硬编码密钥、敏感文件、不安全依赖等 |
| `src/services/hybrid-proofread/cloudSyncClient.ts` | 批量上传文件哈希，获取云端风险结果 |
| `src/services/hybrid-proofread/reportGenerator.ts` | 生成 JSON / HTML / Markdown 报告 |
| `src/store/hybridProofreadStore.ts` | Zustand Store，保存扫描状态、报告、规则版本 |
| `src/config/hybridProofreadConfig.ts` | 静态配置：API 端点、哈希算法、扫描规则、默认包含/排除模式 |
| `scripts/test-tool/test-hybrid-proofread.ts` | Node 脚本入口，用于本地测试 |

> 注意：该模块目前**没有 UI 页面**，也**没有接入数据流水线**。

---

## 二、两套方案的目标与数据边界对比

| 维度 | 数据采集改进方案（上述方案） | 网页测试/检索/校对（hybrid-proofread） |
|------|----------------------------|--------------------------------------|
| **核心目标** | 获取 A 股/市场金融数据，支撑投研分析 | 扫描源代码安全与合规风险，输出审计报告 |
| **输入** | 股票代码、外部行情 API、CSV/Excel 文件 | 本地项目路径（`projectPath`）、源代码文件 |
| **输出** | 规范化行情数据、K 线、批量导入结果 | 安全/合规风险报告（JSON/HTML/Markdown） |
| **主要用户** | 投资者、研究员、投研系统用户 | 开发者、代码审计、CI/发布流程 |
| **数据来源** | 腾讯财经、新浪财经、网易、AKShare、Mock | 本地文件系统 + 云端安全 API |
| **运行时环境** | 浏览器（React / IndexedDB） | 需要 Node.js（`fs`、`crypto`、本地文件遍历） |
| **当前入口** | `DataTestPanel`、`SevenDimConfigPage`、`FetcherConfigPage`、`CollectTaskPage` | 仅有 Node 脚本 `scripts/test-tool/test-hybrid-proofread.ts` |
| **配置方式** | 运行时策略模板、维度优先级、TTL、降级链 | 静态配置对象 `HYBRID_PROOFREAD_CONFIG` |
| **可视化** | 时间线、日志流、泳道图、链路回放、任务面板 | 仅报告文件输出，无实时可视化 |
| **持久化** | `collect_config`、`trace_records`、`stocks` 等 IndexedDB store | 无持久化，报告仅生成到文件 |
| **调度** | `TaskScheduler` 支持轮询/一次性/流式任务 | 手动触发，无调度能力 |

## 三、关键能力逐项比对

### 3.1 配置化

- **数据采集方案**：策略模板 → 维度 → 数据源优先级 → 字段 → 限流/重试/降级/存储/调度，全部运行时可调。
- **hybrid-proofread**：配置为静态对象，规则列表、API 端点、扫描包含/排除模式写死在 `hybridProofreadConfig.ts` 中，缺少运行时 UI 配置能力。

**结论**：若纳入，需要新增大量“规则配置、项目路径、云端 API 密钥”等独立配置项，不属于采集策略配置范畴。

### 3.2 流程可视化

- **数据采集方案**：已落地 `CollectionTimeline`、`LiveLogStream`、`CollectionSwimlane`、`TraceReplayPanel`。
- **hybrid-proofread**：仅有日志输出和最终报告，缺少阶段化 Trace。

**结论**：虽然可以复用可视化组件，但“校对”阶段的语义（本地扫描、规则评估、云端验证）与采集阶段（触发、降级、抓取、写入）不同，需要单独建模。

### 3.3 持久化

- **数据采集方案**：通过 `DataBridge.forward()` 写入 IndexedDB，运行时 Store 启动加载历史 Trace。
- **hybrid-proofread**：无持久化，报告生成到文件系统。

**结论**：可以复用 `trace_records` store 保存校对历史，但需要新增“校对报告”schema，与金融数据分离存储。

### 3.4 任务调度

- **数据采集方案**：`TaskScheduler` 与 `collectionPipeline` 打通，支持显式单次和长期轮询任务。
- **hybrid-proofread**：无调度能力，依赖手动触发或外部 CI 调用。

**结论**：可以复用 `TaskScheduler` 注册“定时安全扫描”任务，但这属于新增功能而非采集方案本身。

### 3.5 运行时环境

- **数据采集方案**：纯浏览器侧即可运行（HTTP fetch + IndexedDB）。
- **hybrid-proofread**：依赖 Node.js `fs` 和 `crypto` 读取本地文件系统，**无法直接在浏览器中运行**。

**结论**：若要在 Web 端纳入，必须提供 Electron/Node 后端或改用 Web File System Access API，成本较高。

## 四、纳入风险与成本

| 风险点 | 等级 | 说明 |
|--------|------|------|
| 业务边界模糊 | 高 | 把代码安全校对混入数据采集，会让配置、Store、UI 承担两类不相关语义，增加维护负担。 |
| 运行时环境不兼容 | 高 | 浏览器无法直接访问本地文件系统，需要重构或新增后端。 |
| 配置模型膨胀 | 中 | 需要新增“项目路径、规则版本、扫描包含/排除、云端 API 凭证”等字段，稀释采集方案专注度。 |
| 可视化语义差异 | 中 | 采集链路阶段（触发/降级/抓取/写入）与校对阶段（扫描/评估/云端验证/报告）不同，需要额外设计。 |
| 门禁与测试成本 | 中 | 新增代码会引入更多 `audit:layers`、`lint:colors`、`tsc` 检查点，且需要独立测试。 |
| 用户心智混淆 | 中 | 投资用户在 SevenDimConfigPage 等页面看到“代码安全扫描”会造成干扰。 |

## 五、可复用的基础设施（不纳入但可对齐）

虽然不建议直接纳入业务，但 `hybrid-proofread` 可以**借鉴并复用**本轮数据采集方案沉淀的基础设施：

| 基础设施 | 复用方式 |
|----------|----------|
| **配置注册表** | 将 `HYBRID_PROOFREAD_CONFIG` 迁移到 `dataSourceRegistry` / `collectConfig` 风格的配置注册表，支持规则模板化。 |
| **流水线 Trace** | 将校对流程拆分为 `proofread:triggered → scan → rule-eval → cloud-check → report → complete` 阶段，接入 EventBus。 |
| **Trace 持久化** | 复用 `tracePersistenceService` 或新增 `proofread_records` store，保存历史校对记录。 |
| **任务调度** | 复用 `TaskScheduler`，注册“定时代码扫描”任务。 |
| **可视化组件** | 复用 `CollectionTimeline`、`LiveLogStream`、`TraceReplayPanel` 的样式与结构，渲染校对阶段。 |
| **颜色/令牌** | 统一使用 `theme.tokens` / `COLOR_TOKENS`，避免硬编码颜色。 |
| **DataBridge** | 报告通过 `DataBridge.forward()` 写入 IndexedDB，便于后续查询和趋势分析。 |

## 六、建议方案

| 方案 | 说明 | 适用场景 |
|------|------|----------|
| **A. 不纳入（推荐）** | 数据采集方案保持聚焦金融数据；`hybrid-proofread` 作为独立模块后续单独升级。 | 当前阶段，避免范围蔓延。 |
| **B. 作为独立子项并行** | 在输入舱（Input Cabin）中新增“项目健康/代码校对”入口，但使用自己的 Store、Service、UI。 | 用户确实需要 Web 化能力时。 |
| **C. 仅在报告中引用** | 在数据采集测试报告中增加“代码安全”章节，但不直接集成校对流程。 | 仅需展示性报告时。 |
| **D. 完全纳入** | 将校对逻辑拆分为浏览器可运行版本，与采集流程合并。 | **不推荐**，成本高、收益低。 |

---

## 七、下一步建议

1. **维持当前数据采集方案范围**：继续完成 SevenDimConfigPage、DataTestPanel、FetcherConfigPage、CollectTaskPage 的剩余任务。
2. **为 `hybrid-proofread` 单独制定升级计划**：
   - 阶段 1：规则配置化（支持运行时规则开关、自定义规则）。
   - 阶段 2：浏览器可运行版本（使用 Web File System Access API 或限定 Electron 环境）。
   - 阶段 3：接入 EventBus + Trace 持久化 + 简单可视化面板。
   - 阶段 4：接入 `TaskScheduler` 支持定时扫描。
3. **若急需入口**，可在配置中心或命令模块中新增“项目健康”入口，避免污染数据采集主链路。
