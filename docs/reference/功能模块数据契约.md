# 功能模块数据契约

> **文档版本**：v1.0
> **创建日期**：2026-06-28
> **文档状态**：🟢 权威生效
> **权威等级**：模块间通信唯一契约标准
> **维护角色**：数据治理架构师
> **适用范围**：`services/scoring/`、`services/trading/`、`services/analysis/`、全局状态 Store 核心功能模块

---

## 文档说明

### 目的

本文档定义 V9 智能投研复盘系统各核心功能模块的输入/输出数据契约，确保模块间数据交换遵循统一的类型定义，解决"双策略一致性"问题。所有模块的实现必须严格遵循本契约规定的数据类型与字段约束。

### 优先级定义

| 优先级 | 标识 | 定义 |
|:---|:---|:---|
| **P0** | 🔴 核心/必选 | 模块运行的基石数据，缺失则功能不可用。任何变更需评审委员会批准。 |
| **P1** | 🟡 重要/推荐 | 支撑核心功能的数据，缺失会导致功能降级。变更需模块负责人审批。 |
| **P2** | 🟢 辅助/可选 | 辅助功能、扩展字段、质量标记。变更可由开发团队自主管理。 |

### 数据来源约定

所有契约中引用的数据类型均以 **`src/data/types.ts`** 为唯一真相源（Single Source of Truth）。模块内部可使用类型别名，但对外接口必须使用标准类型名。

### 命名约定

| 层级 | 命名风格 | 示例 |
|:---|:---|:---|
| 接口/类型 | PascalCase | `HotSectorScore`, `ValuePitAnalyzerInput` |
| 字段/属性 | camelCase | `symbol`, `calculatedAt` |
| 枚举值 | kebab-case | `'hot-sector'`, `'immediate'` |
| Store 名 | snake_case + 复数 | `hot_sector_scores`, `value_pit_scores` |

## 1. 热门板块评分模块（HotSectorAnalyzer）

> **模块路径**：`src/services/scoring/hotSectorAnalyzer.ts`
> **策略定位**：双策略之"热门追涨"——板块已在动，跟着趋势走
> **持有周期**：3–15 天（平均 7 天）
> **止损线**：-8% 硬性止损，不补仓
> **止盈线**：+15% 卖 50%，快进快出

### 1.1 模块总览

| 项目 | 说明 |
|:---|:---|
| **核心功能** | 对热门板块标的进行五维评分，输出综合评分与操作建议 |
| **评分维度** | 动量强度(35%) / 情绪热度(25%) / 技术突破(20%) / 估值风险(15%) / 大盘环境(5%) |
| **前置条件** | V6 个股评分 ≥ `hotSectorV6Min`（默认 3.5） |
| **输出范围** | 综合评分 0–5 分 |
| **操作建议** | `immediate`（立即跟进）/ `probe`（试探）/ `ignore`（不追） |
| **来源定义**：`src/data/types.ts` | — |
| **存储位置**：IndexedDB — `hot_sector_scores` Store | — |

## 3. 轮动信号检测模块（RotationSignalDetector）

> **模块路径**：`src/services/scoring/rotationSignalDetector.ts`
> **策略定位**：价值洼地策略的触发条件引擎——三重验证判定轮动起点

### 3.1 模块总览

## 7. 一致性校验规则

### 7.1 双策略一致性保障

为确保"双策略一致性"，以下规则必须严格遵守：

| 规则编号 | 规则描述 | 优先级 | 校验方式 |
|:---|:---|:---:|:---|
| CON-001 | 热门板块策略与价值洼地策略的输入/输出类型必须统一引用 `src/data/types.ts`，禁止模块内联定义 | P0 | 静态类型检查 + 代码评审 |
| CON-002 | HotSectorScore 与 ValuePitScore 的基础字段（symbol/name/score/calculatedAt/dataVersion）命名与类型必须一致 | P0 | 类型契约测试 |
| CON-003 | 两个策略模块必须使用同一套 `DualStrategyRuleConfig` 配置注入，禁止硬编码阈值 | P0 | 配置审计 + 单测覆盖 |
| CON-004 | 轮动信号检测仅适用于价值洼地策略的 wait/probe 标的，不得用于热门板块策略 | P0 | 逻辑校验 |
| CON-005 | DualStrategyResult 必须整合两策略输出，summary 计数必须与实际数组长度一致 | P0 | 运行时断言 |
| CON-006 | 同一 symbol 不能同时出现在 hotSectorScores 和 valuePitScores 的"入选"列表中（V6 阈值区间互斥） | P1 | 边界测试 |
| **CON-007** | **订单域数据必须以 `src/store/orderStore.ts` 为唯一可信源，禁止在 positionStore / holdingsStore / 组件中重复计算持仓与盈亏** | **P0** | **静态引用检查 + 代码评审** |
| **CON-008** | **OrderStore 通过 DataBridge 订阅 `STORE_NAME.orders` 频道，监听 insertOrder / updateOrder / deleteOrder / tradeActionExecuted，去抖刷新保证跨组件一致性** | **P0** | **运行时订阅测试** |
| **CON-009** | **OrderStore 写操作使用 `MODULE_ID.orderstore` 作为 source，订阅回调中过滤自身 source 防止自激** | **P1** | **代码评审 + 单测** |

> **说明**：CON-007 ~ CON-009 为本次 OrderStore 统一账本新增规则。原分散在各处的持仓/盈亏计算逻辑已收敛到 OrderStore，双策略一致性保障范围从"评分策略"扩展至"订单域数据"。

### 7.2 数据质量标记

所有评分输出必须遵循以下数据质量标记规则：

| 规则编号 | 规则描述 | 优先级 |
|:---|:---|:---:|
| Q-001 | 当任一维度输入使用默认/估算值时，必须在 `qualityWarning` 字段中说明 | P1 |
| Q-002 | 行情数据不足（< 20 根 K 线）时，动量/技术维度得分需标记警告 | P0 |
| Q-003 | 资金流向、北向持仓等外部数据缺失时，需在 qualityWarning 中明确列出 | P1 |
| Q-004 | 大盘环境使用默认值（sideways + medium）时，需标记警告 | P2 |

### 7.3 版本与变更管理

| 规则编号 | 规则描述 | 优先级 |
|:---|:---|:---:|
| V-001 | P0 级类型字段的增删改必须经架构评审委员会批准 | P0 |
