# DataBridge 改进建议整改实施计划

## 一、改进建议汇总

| 优先级 | 建议 | 说明 | 状态 |
|--------|------|------|------|
| P0 | 批量操作支持 | 当前所有 forward 均为单条写入，增加 BULK_* 系列 Action | 待实施 |
| P0 | 细粒度订阅 | 当前按 Store 全量广播，增加 `stocks:{symbol}` 级别订阅 | 待实施 |
| P1 | 事件型频道独立 | 事件型动作混在 DB 路由中，分离事件路由建立 `event:*` 频道体系 | 待实施 |
| P1 | 查询型 forward | 评估是否需要 QUERY_* 系列 Action 统一走 DataBridge | 待实施 |
| P2 | 分布式调度器 | ✅ 已实现 | 已完成 |

---

## 二、可行性评估

### 2.1 P0-1: 批量操作支持

**技术实现难度**：低

- IndexedDB 原生支持 `IDBTransaction` 和批量写入
- 需要新增 BULK_* Action 定义
- 需要新增 BulkHandler 处理器

**资源需求**：低

- 预计修改文件：3个（dbConfig.ts, databridgeHandlers.ts, databridge.ts）
- 预计代码量：200-300 行

**潜在风险**：低

- 向后兼容：新增 Action，不影响现有代码
- 事务边界：批量操作失败需要回滚

**预期效益**：高

- 批量写入性能提升 5-10 倍
- 减少 DB 事务开销
- 降低 Envelope 创建和 ACL 校验的重复成本

### 2.2 P0-2: 细粒度订阅

**技术实现难度**：中

- 需要修改 broadcast() 方法支持模式匹配
- 需要修改 subscribe() 方法支持通配符订阅
- 需要考虑订阅效率（大量 symbol 时的性能）

**资源需求**：中

- 预计修改文件：1个（databridge.ts）
- 预计代码量：150-200 行

**潜在风险**：中

- 性能：大量订阅时的广播效率
- 内存：订阅者 Map 的内存占用

**预期效益**：高

- 减少不必要的订阅通知
- 提升 UI 更新性能
- 降低 EventBus 负载

### 2.3 P1-1: 事件型频道独立

**技术实现难度**：中

- 需要从 DB 路由中分离事件型动作
- 需要建立 `event:*` 频道命名规范
- 需要修改 routeToDB() 方法

**资源需求**：中

- 预计修改文件：2个（databridge.ts, dbConfig.ts）
- 预计代码量：100-150 行

**潜在风险**：低

- 向后兼容：路由逻辑重构，不影响现有 Action

**预期效益**：中

- 代码结构更清晰
- 事件路由与数据路由解耦
- 便于后续扩展事件驱动架构

### 2.4 P1-2: 查询型 forward

**技术实现难度**：低

- 当前 query() 方法已经独立
- 需要评估是否需要将查询也走 forward() 统一入口
- 需要考虑 ACL 校验的一致性

**资源需求**：低

- 预计修改文件：1个（databridge.ts）
- 预计代码量：50-100 行

**潜在风险**：低

- 向后兼容：新增路由分支，不影响现有 query() 方法

**预期效益**：中

- 统一数据入口
- 便于审计和监控
- 简化调用方代码

## 三、实施计划

### 3.1 总体时间安排

| 阶段 | 时间 | 任务 | 交付物 |
|------|------|------|--------|
| 第一阶段 | Day 1 | P0-1 批量操作支持 | BulkHandler、BULK_* Action、测试用例 |
| 第二阶段 | Day 1 | P0-2 细粒度订阅 | 模式匹配订阅、通配符广播、测试用例 |
| 第三阶段 | Day 2 | P1-1 事件型频道独立 | 事件路由分离、event:* 频道体系 |
| 第四阶段 | Day 2 | P1-2 查询型 forward | 查询路由整合、统一入口 |
| 第五阶段 | Day 3 | 测试验证 | 功能测试、性能测试、兼容性测试 |
| 第六阶段 | Day 3 | 报告生成 | 整改报告、问题解决情况、经验总结 |

### 3.2 P0-1: 批量操作支持 - 详细计划

**目标**：实现 BULK_INSERT_STOCK、BULK_SAVE_DAILY_QUOTES、BULK_SAVE_SCORES 等批量操作

**步骤**：

1. **Action 定义**：在 `dbConfig.ts` 中新增 BULK_* 系列 Action
2. **Handler 实现**：在 `databridgeHandlers.ts` 中新增 `BulkHandler` 类
3. **路由映射**：在 `databridge.ts` 的 `ACTION_TO_STORE_MAP` 中添加映射
4. **注册 Handler**：在 `createHandlerRegistry()` 中注册 `BulkHandler`
5. **测试验证**：编写单元测试验证批量写入功能

**关键技术点**：

- 使用 IndexedDB 事务进行批量写入
- 批量操作失败时需要完整回滚
- 保持与单条操作相同的 ACL 校验和审计日志

### 3.3 P0-2: 细粒度订阅 - 详细计划

**目标**：支持 `stocks:{symbol}` 级别的订阅，订阅者只接收关注股票的变更

**步骤**：

1. **订阅模式扩展**：修改 `subscribe()` 方法支持通配符（`stocks:*`）
2. **广播模式匹配**：修改 `broadcast()` 方法支持模式匹配广播
3. **符号级广播**：在写操作时同时广播 Store 级和 symbol 级频道
4. **测试验证**：编写单元测试验证细粒度订阅功能

**关键技术点**：

- 订阅者按模式分组存储
- 广播时同时匹配精确频道和模式频道
- 避免大量 symbol 订阅时的性能问题

### 3.4 P1-1: 事件型频道独立 - 详细计划

**目标**：将事件型动作从 DB 路由中分离，建立独立的 `event:*` 频道体系

**步骤**：

1. **事件 Action 识别**：识别当前混在 DB 路由中的事件型动作
2. **路由分离**：在 `forward()` 方法中新增 `routeToEvent()` 路由分支
3. **频道命名规范**：建立 `event:*` 频道命名规范
4. **测试验证**：编写单元测试验证事件路由功能

**关键技术点**：

- 事件型动作不写入数据库
- 事件路由只触发广播
- 保持向后兼容

### 3.5 P1-2: 查询型 forward - 详细计划

**目标**：评估并实现 QUERY_* 系列 Action 统一走 DataBridge forward()

**步骤**：

1. **需求评估**：确认是否需要将查询操作也统一走 forward()
2. **路由扩展**：在 `forward()` 方法中新增查询路由分支
3. **测试验证**：编写单元测试验证查询路由功能

**关键技术点**：

- 查询操作不需要事务
- 查询操作需要缓存支持
- 保持与现有 query() 方法的一致性

## 四、风险与应对

| 风险 | 级别 | 应对策略 |
|------|------|---------|
| 批量操作事务失败 | 中 | 使用 IndexedDB 事务，失败时回滚 |
| 细粒度订阅性能下降 | 中 | 订阅者按模式分组，广播时批量匹配 |
| 路由重构影响现有功能 | 低 | 保持向后兼容，新增路由不修改现有逻辑 |
| 查询性能下降 | 低 | 查询路由复用现有缓存机制 |
