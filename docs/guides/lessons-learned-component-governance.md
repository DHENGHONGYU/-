## 第一部分：治理背景与核心发现

### 1.1 项目概况

| 项目 | FinSightV9（智能投研复盘系统） |
|------|-------------------------------|
| 治理时间 | 2026 年 7 月（P2 密集开发期后） |
| 扫描范围 | `src/components/` 下 30+ 僵尸组件，8 大类别 |
| 治理批次 | P2 批次僵尸清理（23 个组件 + 1 个孤岛页面） |
| 涉及层级 | atoms / molecules / organisms / cabin / chart / search |

### 1.2 核心发现

**反直觉结论：大部分僵尸组件不是 V6 遗留，而是 V9 自身 P2 密集开发期（7/14-7/18）的产物。**

在传统认知中，僵尸代码通常被归因于历史遗留或技术迁移。但本次深度诊断揭示了一个更值得警惕的事实：**在快速迭代的密集开发期，新写的代码比旧代码更容易变成僵尸。**

原因分析：

- **P2 期并行推进 5+ 模块**，各模块独立开发，缺少全局视角
- **先搭框架再填业务**的开发顺序，导致框架组件写好了但业务最终没接入
- **组件化过度拆分**，为了"遵循原子设计"而硬拆分子组件，结果子组件从未被复用
- **设计系统储备冲动**，参考 Ant Design 等成熟库提前储备组件，但实际业务用不上

### 1.3 8 大僵尸类别概览

| 类别 | 典型组件 | 数量 | 占比 | 根因 |
|------|---------|------|------|------|
| **设计系统冗余** | DatePicker, Grid, List, Menu, Pagination, Popover | 6 个 | ~26% | 设计系统新增无准入门槛，前瞻性储备冲动 |
| **未完成功能** | SearchBar, SearchFilters, SearchResultList, GroupedView, TimelineView（整个 search 目录） | 5 个 | ~22% | 模块孤岛化开发，有组件无入口 |
| **功能孤岛** | MultiFactorFilterPanel（已修复）、StatusQueryPanel | 2 个 | ~9% | 先组件后集成脱节，组件写完没挂路由 |
| **分子冗余** | FilterChip（旧版）、FormField | 2 个 | ~9% | 命名冲突致隐性废弃，新旧版本并存 |
| **模板冗余** | Result 组件 | 1 个 | ~4% | 功能重复，被 EmptyState/ErrorState 替代 |
| **Cabin 评分旧版** | ScoreHistoryTable, ScoreItem, ScoreSnapshot, ScoreSummary（旧 cabin 实现） | 4 个 | ~17% | 架构迭代，旧实现未及时清理 |
| **图表未集成** | IndustryV4Panel, IndustryV4Radar, SubIndicatorBar, TrendLineChart, ValuationDistribution | 5 个 | ~22% | 先组件后集成，chart/industry 全套做完但消费方 TBD |
| **其他零散** | LoopBanner, ProfileBrowsePage（915 行孤岛页面） | 2 个 | ~9% | 半成品页面，无路由无入口 |

> **注**：部分组件跨多个类别，占比之和超过 100%。统计基于 P2 批次清理的 23 个组件 + 1 个孤岛页面。

### 1.4 治理成效

- 删除僵尸组件 23 个，释放代码约 3500+ 行
- 删除孤岛页面 1 个（ProfileBrowsePage，915 行）
- 删除无引用 JSON Schema 目录 1 个（6 个文件）
- 建立三道防线：增量零容忍 + 存量预警 + 季度清理
- 落地三项制度：组件准入政策、生命周期 SOP、模块完成标准

## 第二部分：6 大根因复盘

每个根因按"现象 → 本质 → 本次解决方案 → 预防措施"四段式展开。

### 根因 1：先组件后集成脱节

**现象**

组件代码写得很完整，测试也有，文档也齐，但就是没有消费方。典型如 `chart/industry/` 下的 5 个图表组件（IndustryV4Panel、IndustryV4Radar、SubIndicatorBar、TrendLineChart、ValuationDistribution），全套实现做完了，consumers 字段填的是 `TBD - pending integration`，然后就一直 pending 下去了。

search 模块的 5 个组件也是同样模式：SearchBar、SearchFilters、SearchResultList、GroupedView、TimelineView 全部实现完毕，但从未挂到任何页面路由上。

**本质**

开发顺序倒置了。正确的顺序应该是"业务需求 → 页面集成 → 抽离组件"，但实际操作中变成了"组件先行 → 等待集成 → 集成搁置 → 组件僵尸"。

背后的心理动因：
- **确定性偏好**：写组件是确定性工作，需求清晰，产出可见；集成涉及多方协调，不确定性高
- **成就感驱动**：组件写完就能看到效果，集成需要等其他模块配合
- **任务拆分不合理**：把"开发组件"和"接入业务"拆成了两个独立任务，前者完成后者没人跟进

**本次解决方案**

1. 对已确认无消费方的 chart/industry 5 个组件和 search 5 个组件，全部标记删除
2. 对有潜在价值但暂时无消费方的组件（如 MultiFactorFilterPanel），补路由接入，挂到 `/analysis/multi-factor` 路径
3. 在 componentRegistry 中强制要求 consumers 字段不能为空（active 状态组件），禁止 `TBD` 占位

**预防措施**

- **消费方先行原则**：没有明确的消费方就不写组件。至少有一个页面或上层组件明确 import 使用，方可立项开发
- **完成=可用**：组件开发完成的定义是"已被业务代码实际使用"，而非"代码写完了"
- **PR 联动检查**：新增组件的 PR 必须同时包含至少一个消费方的 import 代码，否则不予合并
- **WIP 倒计时**：如果确实需要先开发组件（如跨团队协作），标记为 wip 状态并设置最长 2 个迭代的存活期

---

### 根因 2：注册表与实际使用脱节

**现象**

`componentRegistry.ts` 中登记的组件状态与实际使用情况不一致。典型问题：

- 标记为 `active` 的组件，实际零引用（如 FormField、SearchBar 等）
- 已废弃的组件，registry 中仍显示 `active`
- `consumers` 字段写的是预期消费方，而非实际消费方
- 有些组件根本没在 registry 中登记，成为"黑户组件"

**本质**

注册表变成了"登记即忘"的静态清单，而不是动态维护的真相源。登记时满腔热情填了一堆信息，之后再也不更新。注册表与实际使用之间没有自动校验机制，全靠人工自觉维护，结果就是逐步失真。

**本次解决方案**

1. 全量审计 componentRegistry，逐一核实每个组件的实际引用次数
2. 将零引用的 active 组件改为 `wip` 或 `deprecated` 状态，补充 deprecationMeta
3. 修正 consumers 字段，从"预期消费方"改为"实际消费方"
4. 建立 `audit:atomic` 脚本，校验组件是否按层级正确放置、是否在 registry 中登记

**预防措施**

- **注册表即真相源**：componentRegistry 是组件状态的唯一权威来源，必须与代码实际状态一致
- **audit:atomic 强制校验**：CI 中运行原子分层审计，未登记或登记信息不一致的组件触发 violation
- **consumers 字段硬校验**：active 状态组件的 consumers 列表中，至少有一个消费方能在代码中找到实际 import
- **变更同步更新**：组件迁移、重命名、废弃时，必须同步更新 registry，由 code review 把关

### 根因 3：模块孤岛化开发

**现象**

各模块独立开发，互相不通气，导致：

- MultiFactorFilterPanel 组件全链路存活，但从未挂路由，用户根本访问不到
- StatusQueryPanel 做了完整功能，但在主流程中没有入口
- ProfileBrowsePage 写了 915 行代码，无路由、无导航、无任何引用
- 搜索模块 5 件套全部实现，但搜索功能在产品路线图中优先级已下调

这些模块从内部看"功能都做好了"，从用户视角看"根本不存在"。

**本质**

按模块分工开发时，每个人只关心自己模块的内部完整性，不关心"用户能不能用到"。模块的完成标准退化成了"代码写完了"，而不是"用户可以用了"。

更深层的问题是缺少一个全局的"入口层"视角——没有人对"功能是否可达"负责，大家都对"我的代码对不对"负责。

**本次解决方案**

1. 对有价值的孤岛功能（MultiFactorFilterPanel），补路由接入分析舱
2. 对无明确价值的孤岛模块（search 全套、StatusQueryPanel），标记废弃并删除
3. 对超大孤岛页面（ProfileBrowsePage，915 行），确认无路由无入口后删除
4. 制定《模块完成标准（DoD）》，明确 6 要素：类型层、服务层、状态层、UI 层、入口层、文档层

**预防措施**

- **模块 DoD 强制准入**：新模块必须满足 6 要素才能标记完成，其中"入口层"是硬门槛
- **入口层最后验证**：模块开发完成后，从"用户能否发现并使用"的视角做最终验收
- **路由审计自动化**：`audit:routes` 脚本检查有页面无路由、有路由无页面的漂移
- **moduleManifest 统一管理**：所有模块在 moduleManifest.ts 中登记状态，active 模块必须有对应入口

### 根因 4：设计系统新增无准入门槛

**现象**

atoms 层一次性新增了 DatePicker、Grid、List、Menu、Pagination、Popover、Result 等 7 个组件，全部零业务引用。这些组件的共同特点是：参考 Ant Design 等成熟组件库，觉得"将来肯定用得上"，于是提前做了储备。结果项目上线几个月了，一个都没用上。

更严重的是，这些"储备组件"还占用了设计系统的维护成本——改设计令牌时要同步更新，做类型迁移时要同步修改，跑测试时要执行它们的用例。

**本质**

设计系统陷入了"大而全"的误区，把"组件数量多"等同于"设计系统成熟"。但实际上，**没有消费方的组件不是资产，是债务**。每一个未被使用的组件都在消耗维护成本，却不产生任何价值。

背后的认知偏差：
- **锚定效应**：以成熟组件库（Ant Design、Material UI）为锚点，觉得别人有的我们也应该有
- **预判偏差**：高估了未来对这些组件的需求，低估了维护成本
- **完整性执念**：追求设计系统的"完整性"，觉得缺了某个组件就是不完整

**本次解决方案**

1. 删除 7 个零引用的原子组件（DatePicker、Grid、List、Menu、Pagination、Popover、Result）
2. 制定《组件新增准入政策》，明确消费方先行原则和最小可用原则
3. 建立前瞻性储备申请流程，需经前端负责人和架构负责人双审
4. WIP 组件设最长存活期（2 个迭代），超期自动降级

**预防措施**

- **准入 Checklist**：新增组件必须通过 5 大类检查（业务需求验证、注册登记、消费方验证、质量保障、导出引用），详见准入政策
- **消费方先行**：至少有一个实际业务场景驱动，禁止"可能会用到"的预判式开发
- **最小可用**：只实现当前需求需要的 props 和能力，不提前做扩展
- **储备审批制**：确需前瞻性储备的组件，需提交正式申请并经两级审批

### 根因 5：命名冲突致隐性废弃

**现象**

项目中存在多组功能相似但命名不同的组件，导致其中一套实际上被废弃了，但代码还在：

- FilterChip 有两个实现（molecules 层和 organisms 层），其中一个从未被使用
- ErrorState 有两个版本（molecules/ErrorState.tsx 和 molecules/states/Error.tsx）
- Skeleton 同理，atoms 层和 molecules/states 层各有一份
- FormField 组件做了一半，后来有了新的实现方向，旧的没删

这些"隐性废弃"的组件比明确标记 deprecated 的组件更危险——后者至少大家知道不要用，前者则可能被新人误用，导致技术债务扩散。

**本质**

组件迭代时只做"加法"不做"减法"。新方案出来了，旧方案不删除，美其名曰"兼容"或"留着参考"。时间一长，谁也记不清哪个是在用的、哪个是废弃的。

命名冲突的另一个来源是跨模块重名——不同模块各自实现了同名组件，功能略有差异，互不知道对方的存在。

**本次解决方案**

1. 清理重复实现，保留活跃使用的版本，删除零引用版本
2. 统一状态组件命名规范，将 molecules/states/ 下的组件明确为 P3 交互状态组件
3. 在 componentRegistry 中增加命名唯一性校验，不允许同名组件
4. 废弃组件必须显式标记 `@deprecated` 并说明替代方案

**预防措施**

- **命名唯一原则**：全项目不允许同名组件，新增前必须全局搜索确认
- **废弃必显式**：旧组件被新组件替代时，必须立即标记 @deprecated，不能"悄悄废弃"
- **替代必删除**：新方案稳定运行 1 个迭代后，旧方案必须删除，不能无限期并存
- **命名规范审查**：Code Review 时检查组件命名是否与现有组件冲突

### 根因 6：死代码审计有工具无闭环

**现象**

项目早就有 `audit:deadcode` 脚本，可以扫描未使用组件。但：

- 扫描结果仅为 warning 级别，不阻断提交
- 报告生成后没人跟进处理，僵尸组件越积越多
- 增量代码没有门禁，新的僵尸组件持续产生
- 缺少明确的废弃流程和定期清理机制

一句话总结：**有审计工具，但没有闭环流程。审计了等于没审计。**

**本质**

工具只是手段，闭环才是目的。很多团队引入了各种审计工具，觉得"我们有代码质量保障"，但如果审计结果不与行动挂钩，工具就只是摆设。

死代码治理需要三道防线：增量零容忍（不让新僵尸进来）、存量预警（持续监控存量）、定期清理（集中处理积压）。缺少任何一道，僵尸组件都会卷土重来。

**本次解决方案**

1. **增量零容忍**：在 `gate:dev` 和 `gate:quick` 中加入 `audit:deadcode --staged`，暂存区新增的零引用组件直接阻断提交（exit 1）
2. **存量预警**：全量 `audit:deadcode` 保持 warning 级别，持续监控存量
3. **季度清理 SOP**：制定《组件全生命周期管理与季度僵尸组件清理 SOP》，建立季度清理节奏
4. **生命周期管理**：定义新增准入、活跃维护、观察预警、废弃流程、季度清理五个阶段的完整闭环

**预防措施**

- **增量门禁硬约束**：`gate:dev` 中的 `--staged` 模式必须为 exit 1，不能降级为 warning
- **季度清理制度化**：每季度首月启动清理，按审计-确认-标记-验证-删除五阶段执行
- **观察列表机制**：引用次数为 1 的组件进入观察列表，跟踪唯一消费者的状态
- **责任到人**：每个待清理组件分配明确的负责人，避免"集体负责 = 没人负责"

## 第三部分：二次开发黄金法则（10 条）

以下 10 条法则从本次治理经验中提炼，适用于所有二次开发场景。每条都配了正反例，确保可操作、不空泛。

### 法则 1：消费方先行——没有明确消费者就不写组件

**原则**：组件必须由实际业务需求驱动，至少有一个页面或上层组件明确需要使用，方可立项开发。

**正例**：
> "股票池页面需要一个可排序、可多选的表格，抽成 Table 组件复用" → 允许。先有 PoolList 页面的实际需求，再抽 Table 组件。

**反例**：
> "我觉得将来可能需要一个 DatePicker 组件，先做出来放着" → 禁止。结果就是 P2 期那 7 个原子组件的下场——零引用躺平几个月后被删。

**检验方法**：写组件前先问自己——"哪个页面或哪个上层组件会 import 这个组件？"如果答不上来，就别写。

---

### 法则 2：完成=可用——有代码无入口=半成品

**原则**：功能完成的定义是"用户可以发现并使用"，而不是"代码写完了"。代码写好了但用户找不到、用不了，那就是半成品，不能标记为 done。

**正例**：
> MultiFactorFilterPanel 组件开发完成 → 挂到 `/analysis/multi-factor` 路由 → 导航菜单中添加入口 → 用户可以从首页 3 次点击内到达 → 标记完成。

**反例**：
> ProfileBrowsePage 写了 915 行代码，UI 很精美，但没有路由注册，没有导航入口，只有开发者知道 URL → 这是半成品，不是完成。最终被整体删除。

**检验方法**：假装你是第一次使用产品的用户，能不能在 3 次点击内找到这个功能？不能就是入口层有问题。

---

### 法则 3：增量零容忍——PR 新增的未使用组件不能合入

**原则**：新提交的代码中如果包含零引用的组件，直接阻断合入。存量可以慢慢清，但增量绝对不能再放。

**正例**：
> 开发新组件时，同步在消费方页面 import 并使用，PR 中同时包含组件代码和调用代码，`gate:dev` 的 `audit:deadcode --staged` 检查通过。

**反例**：
> 只提交组件代码，说"后面再接"，然后就没有然后了。`audit:deadcode --staged` 检测到零引用，exit 1 阻断提交。

**检验方法**：`npm run gate:dev` 全绿，其中 `audit:deadcode --staged` 必须通过。

---

### 法则 4：命名唯一——全项目不允许同名组件

**原则**：组件名在整个项目中必须唯一。新增组件前全局搜索确认，不同模块不允许各自实现同名组件。

**正例**：
> 发现 molecules 层已经有 ErrorState，需要新增状态类组件时，命名为 ErrorStateIndicator 或其他不冲突的名称，并在 registry 中明确区分用途。

**反例**：
> atoms 层有 Skeleton，molecules/states 层也有 Skeleton，新人不知道用哪个，随便 import 一个，导致风格不一致。最终花时间清理重复实现。

**检验方法**：新增组件前，`rg "export.*function.*ComponentName" src/` 确认没有重名；Code Review 时 reviewer 也要检查命名冲突。

---

### 法则 5：分层清晰——原子/分子做通用，有机体做业务

**原则**：严格遵守原子设计分层原则，不同层级的组件有明确的职责边界，不跨层越界。

**分层规则**：

| 层级 | 职责 | 可依赖 | 不可依赖 |
|------|------|--------|----------|
| **Atom** | 纯样式封装，最小 UI 单元 | Tailwind / Tokens | Store / Service / 业务 |
| **Molecule** | 原子组合，无业务逻辑 | Atoms | Organism / Store / 业务 |
| **Organism** | 业务领域复合组件 | 任意层级 | — |
| **Template** | 页面布局骨架 | Molecule + Atom | 业务数据 / Store / Service |

**正例**：
> Button（atom）只封装样式和基础交互；Alert（molecule）组合 Icon + Text + CloseButton；PoolBoard（organism）调用 usePoolStore 获取数据并渲染 PoolCard 列表。分层清晰，各司其职。

**反例**：
> 一个 molecule 组件里直接 import 了 usePoolStore，获取股票池数据并渲染——这已经是 organism 了，放错了层级。结果就是 `audit:atomic` 报 violation。

**检验方法**：`npm run audit:atomic` 零 violation。判断一个组件属于哪层，看它有没有 import Store/Service，有就是 organism，没有再看是不是组合了其他组件。

---

### 法则 6：最小可用——不做前瞻性储备，只做当前需要的

**原则**：组件功能范围严格限定在当前迭代的实际需求内，不提前实现"将来可能需要"的 props、variant 或能力。预留扩展空间即可，功能随消费方增长逐步迭代。

**正例**：
> 当前页面只需要 Table 组件支持排序和行选择，那就只实现这两个功能。分页、虚拟滚动、列固定等将来真的需要了再加。

**反例**：
> 参考 Ant Design 的 Table 组件，一次性实现 20 个 props、5 种 variant，结果当前项目只用上了 3 个 props。多余的代码不仅没用，还增加了维护成本。

**检验方法**：检查组件的 props 列表，每一个 prop 都能找到实际使用方吗？找不到的就是过度设计，删掉。

---

### 法则 7：入口层必验——模块完成前，先验证用户能不能找到

**原则**：每个模块开发完成后，必须从"用户视角"做入口层验证——用户能否通过正常操作路径发现并使用该功能。这是模块 DoD 的硬门槛。

**正例**：
> 开发完复盘向导功能后，验证路径：首页 → 点击"输出"导航 → 点击"复盘向导"卡片 → 进入向导页面 → 走完主流程。全程不超过 3 次点击，入口可见，流程通畅。

**反例**：
> 开发完一个数据导入功能，只在代码里注册了路由 `/import/bulk`，但导航菜单里没有入口，用户根本不知道有这个功能。这就是典型的"功能孤岛"。

**检验方法**：
- 从首页出发，3 次点击内能到达吗？
- 导航菜单或功能列表中有入口吗？
- 新用户不看文档能找到这个功能吗？

---

### 法则 8：废弃必显式——旧方案不能"悄悄废弃"

**原则**：当组件被新方案替代时，旧组件必须立即标记 `@deprecated`，说明替代方案和计划删除日期。不能因为"懒得写注释"或"怕影响别人"而不标记。

**正例**：
> 新的评分卡片组件 ScoreCard 替代了旧的 ScoreItem。旧组件顶部立即添加 JSDoc：
> ```tsx
> /**
>  * @deprecated 自 v2.0.0 起废弃，请使用 ScoreCard 替代
>  * 计划删除日期：2026-09-01
>  * 废弃原因：功能被 ScoreCard 统一替代，交互更丰富
>  */
> ```
> 同时在 componentRegistry 中标记 status: 'deprecated'，填写 deprecationMeta。

**反例**：
> 新组件做好了，开发人员都知道用新的，但旧组件没加任何标记，也没改 registry 状态。新人进来看到旧组件，以为是在用的，结果误用了废弃实现。

**检验方法**：
- 旧组件文件顶部有 `@deprecated` JSDoc 吗？
- componentRegistry 中 status 是 'deprecated' 吗？
- deprecationMeta 中填了替代组件和计划删除日期吗？

---

### 法则 9：文档同步——代码变更必须同步更新文档和注册表

**原则**：任何组件的新增、修改、重命名、废弃、删除，都必须同步更新 componentRegistry、相关文档和索引。代码和文档是一体的，只改代码不改文档等于只做了一半。

**正例**：
> 删除一个组件时，同步执行以下操作：
> 1. 删除组件源文件
> 2. 从 barrel index.ts 中移除导出
> 3. 从 componentRegistry.ts 中移除登记
> 4. 更新相关文档中的引用
> 5. 在 CHANGELOG 中记录删除项

**反例**：
> 组件删除了，但 componentRegistry 里还留着记录，文档里还在引用这个组件。新人按照文档找组件，发现找不到，浪费时间排查。

**检验方法**：
- componentRegistry 中的组件列表与实际文件一致吗？
- 文档中提到的组件都是真实存在的吗？
- `audit:docs` 文档同步检查通过吗？

---

### 法则 10：定期清债——技术债务不能只积累不清偿

**原则**：死代码、僵尸组件、废弃模块等技术债务必须定期清理，不能"等有空再说"。"有空"永远不会来，债务只会越积越多，最终拖垮整个项目。

**正例**：
> 按季度执行僵尸组件清理：
> - 季度首月第 1 周：全量审计，生成待清理清单
> - 季度首月第 2-3 周：分配负责人，确认废弃/保留
> - 季度首月第 4 周：批量标记 deprecated
> - 季度中月：验证无新增引用，推进迁移
> - 季度末月：执行删除，提交清理 PR

**反例**：
> "这些组件先留着吧，以后可能用得上" → 半年后再看，组件数量翻了一倍，没人敢删（怕删错），也没人敢用（不知道哪个是活的）。技术债务进入恶性循环。

**检验方法**：
- 上季度的僵尸组件清理了吗？
- 当前零引用组件数量比上季度减少了吗？
- WIP 状态组件有没有超期的？

---

## 第四部分：常见陷阱与避坑指南

### 陷阱 1："先写了再说，后面总会用到"

**典型心态**
> "这个组件虽然现在没人用，但功能这么通用，以后肯定有地方用。先写了放着，总比到时候再写强。"

**现实打脸**
90% 的概率用不到。本次治理中，7 个"前瞻性储备"的原子组件（DatePicker、Grid、List、Menu、Pagination、Popover、Result）全部零引用，躺平几个月后被删除。chart/industry 下 5 个图表组件也是同样命运。

**为什么会这样**
- 未来的需求往往和你预想的不一样，到时候还是要改
- 就算需求对得上，到时候组件的 API 设计、样式风格可能已经不匹配了
- 组件放久了没人维护，依赖升级、类型变更都可能让它坏掉，用的时候反而要花更多时间修

**避坑方法**
1. 严格执行消费方先行原则，没有明确消费方就不写
2. 确有前瞻性需求的，走正式的储备申请流程，两级审批
3. 储备组件设有效期（最多 2 个迭代），到期没接上就删

---

### 陷阱 2："按模块分工容易孤岛"

**典型现象**
> 团队按模块分工，每人负责一个模块。大家都把自己模块的内部逻辑写得很完善，但模块之间不通气，结果就是：每个模块内部看都没问题，但拼起来发现很多功能用户根本访问不到。

**现实案例**
- MultiFactorFilterPanel：组件全链路存活，但从未挂路由，成为功能孤岛
- StatusQueryPanel：功能完整，但主流程中没有入口
- search 模块 5 件套：全部实现完毕，但产品优先级已下调，功能永不接入

**为什么会这样**
- 每个人的 KPI 是"我的模块做完了"，不是"用户能用我的功能了"
- 缺少全局的产品视角和入口层验收
- 模块之间缺少协调机制，各自为政

**避坑方法**
1. 模块 DoD 6 要素强制准入，其中"入口层"是硬门槛
2. 每个迭代末做一次"功能可达性巡检"，从用户视角走一遍所有功能
3. `audit:routes` + `audit:deadcode` 双重检查，发现孤岛模块及时处理
4. 产品经理参与验收，从用户视角确认功能可达

---

### 陷阱 3："组件库要大而全"

**典型心态**
> "成熟的组件库应该有丰富的组件。我们现在组件太少了，得多做几个，把组件库充实起来。"

**现实打脸**
组件数量 ≠ 组件库质量。本次清理的 23 个僵尸组件中，有 6 个是为了"充实组件库"而做的通用原子组件，结果一个都没用上。它们不仅没产生价值，还增加了维护成本——改设计令牌时要同步更新，跑测试时要执行它们的用例，新人入职时要学习它们的 API。

**为什么会这样**
- 把"组件数量多"等同于"设计系统成熟"，这是认知偏差
- 成熟组件库（Ant Design 等）有专门的团队维护，而我们没有
- 通用组件的设计成本很高，要考虑各种边界情况和可扩展性，业务驱动的组件反而简单

**避坑方法**
1. 记住：没有消费方的组件不是资产，是债务
2. 组件库建设走"业务驱动"路线，需要什么做什么
3. 组件质量比数量重要——把在用的组件做好、做精，比堆数量有价值
4. 定期统计组件的引用次数和复用率，用数据说话

---

### 陷阱 4："两套方案都做了再选"

**典型现象**
> 开发一个功能时，不确定哪种方案更好，于是两套都做了，说"先放着对比一下"。结果对比完选中了 A 方案，B 方案的代码忘了删，就一直躺在代码库里。

**现实案例**
- ErrorState 有两个实现（molecules/ErrorState.tsx 和 molecules/states/Error.tsx），其中一个从未被使用
- Skeleton 同理，atoms 层和 molecules/states 层各有一份
- FilterChip 有两个版本，旧版零引用但没删

**为什么会这样**
- 做技术选型时喜欢"做出来比比看"，但忘了清理落选方案
- 怕以后方案 A 不行还能回退到 B，结果永远也不会回退
- "留着参考"心态——觉得代码写都写了，删了可惜

**避坑方法**
1. 技术选型尽量在设计阶段决定，不要写了代码再选
2. 必须做原型对比的，在分支上做，对比完删除落选分支
3. 选中方案稳定运行 1 个迭代后，必须删除落选方案的代码
4. 旧组件被新组件替代时，旧组件立即标记 @deprecated 并设删除日期

---

### 陷阱 5："审计工具跑了就行"

**典型心态**
> "我们有 audit:deadcode 脚本，每次 CI 都会跑，死代码问题不用担心。"

**现实打脸**
有工具没闭环 = 没有工具。本次治理前，`audit:deadcode` 已经存在很久了，但僵尸组件还是越积越多。为什么？因为：
- 审计结果只是 warning，不阻断提交
- 报告生成后没人看、没人跟进
- 只有全量扫描，没有增量门禁，新僵尸持续涌入
- 没有定期清理机制，存量只增不减

**为什么会这样**
- 把"引入工具"等同于"解决问题"，忽略了流程和人的因素
- 工具只负责"发现问题"，但"解决问题"需要人来执行
- 没有把审计结果与行动挂钩，工具成了摆设

**避坑方法**
1. **三道防线**：增量零容忍（gate:dev）+ 存量预警（全量 audit）+ 季度清理（SOP）
2. **增量硬约束**：`audit:deadcode --staged` 必须是 exit 1，不能降级
3. **定期清理制度化**：每季度执行一次清理，有流程、有责任人、有时间节点
4. **结果可视化**：僵尸组件数量趋势图贴出来，让团队看到债务是在增加还是减少

---

## 第五部分：快速检查清单

供开发人员自查和 Review 人员使用。

### 5.1 新组件自查 Checklist（8 项）

开发新组件前 / 提交 PR 前，逐项确认：

- [ ] **有明确消费方**：至少有一个页面或上层组件会 import 并使用这个组件（能说出具体文件名）
- [ ] **命名唯一**：全局搜索确认组件名不与现有组件冲突
- [ ] **层级正确**：组件放在正确的目录层级（atoms / molecules / organisms / templates），不跨层越界
- [ ] **最小可用**：只实现当前需求需要的功能，没有多余的"预留 props"或"未来扩展"
- [ ] **注册登记**：已在 `componentRegistry.ts` 中登记，consumers 字段填写实际消费方
- [ ] **有测试覆盖**：核心交互有单元测试（Atom：快照 + 事件；Molecule：功能 + 边界；Organism：Store 交互 + 主流程）
- [ ] **有文档注释**：组件顶部有 JSDoc 说明用途，Props 有注释
- [ ] **门禁通过**：`npm run gate:dev` 全绿，包括 `audit:deadcode --staged`、`audit:atomic`、`lint:colors`

---

### 5.2 新模块自查 Checklist（6 要素）

新功能模块开发完成后，对照 DoD 6 要素确认：

- [ ] **类型层**：模块核心数据结构有类型定义，存放在 `src/types/modules/` 下，`typecheck` 通过
- [ ] **服务层**：业务逻辑封装在 Service 中，写操作走 DataBridge 信封协议，`audit:layers` 零 violation
- [ ] **状态层**：Store 实现完整，有 init/fetch/reset 方法，有 withBroadcast 中间件，有测试覆盖
- [ ] **UI 层**：页面/组件实现完整，有 loading/empty/error 三态处理，颜色使用设计令牌
- [ ] **入口层**：有明确的访问入口（路由/菜单/按钮），从首页出发 3 次点击内可达，`audit:routes` 通过
- [ ] **文档层**：有功能说明文档（面向用户）和技术文档（面向开发者），模块在功能清单中有登记

---

### 5.3 PR Review 检查清单（5 项）

Review 他人 PR 时，特别关注以下几点：

- [ ] **新增组件有消费方吗？** 检查 PR 中新增的组件，是否同时有消费方 import 使用。只有组件没有调用方的，打回
- [ ] **componentRegistry 同步更新了吗？** 新增/修改/删除组件时，registry 是否同步变更
- [ ] **命名有冲突吗？** 新组件名是否与现有组件重名，是否符合命名规范
- [ ] **分层正确吗？** 组件放在正确的层级吗？有没有跨层依赖（如 molecule import 了 store）
- [ ] **入口层验证了吗？** 如果是新功能模块，有没有路由注册和导航入口

## 第六部分：相关工具与文档索引

### 6.1 审计命令速查

| 命令 | 用途 | 退出码 | 适用场景 |
|------|------|--------|----------|
| `npm run audit:deadcode` | 全量死代码审计，输出未使用组件清单 | 0=仅warning, 1=有violation | 存量监控、季度清理 |
| `npm run audit:deadcode -- --staged` | 增量死代码审计（仅检查暂存区） | 0=通过, 1=阻断 | 提交前自查、CI 门禁 |
| `npm run audit:registry` | 注册表审计，检查动态注册组件 | 视配置而定 | 验证 widget/agent 注册完整性 |
| `npm run audit:atomic` | 原子分层合规审计 | 0=通过, 1=违规 | 组件分层检查、CI 门禁 |
| `npm run audit:routes` | 路由一致性审计 | 视配置而定 | 孤岛模块检测、入口层验证 |
| `npm run gate:dev` | 开发门禁（全量检查） | 0=通过, 1=阻断 | 提交前完整检查 |
| `npm run gate:quick` | 快速门禁（核心检查） | 0=通过, 1=阻断 | 快速验证、轻量 PR |

**日常开发推荐命令组合**：
```bash
# 提交前快速自检
npm run gate:quick

# 提交前完整检查
npm run gate:dev

# 仅检查组件相关
npm run audit:atomic && npm run audit:deadcode -- --staged
```
