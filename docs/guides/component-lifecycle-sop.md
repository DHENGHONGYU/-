# 组件全生命周期管理与季度僵尸组件清理 SOP

> 文档版本：v1.0
> 生效日期：2026-07-25
> 适用范围：FinSightV9 项目 `src/components/` 下所有组件

---

## 1. 背景与目标

### 1.1 问题根因

项目存在"有审计工具但无闭环"的死代码问题：

- `audit:deadcode` 脚本可以扫描出未使用组件，但结果仅为 warning 级别，不阻断提交
- 存量僵尸组件越积越多，新组件也可能因为疏忽而成为死代码
- 缺少明确的组件废弃流程和定期清理机制

### 1.2 闭环方案

通过三道防线构建死代码审计闭环：

| 防线 | 机制 | 工具 | 力度 |
|------|------|------|------|
| 增量零容忍 | 新提交的组件必须有引用，否则阻断提交 | `--staged` 模式 + gate:dev/gate:quick | 强（exit 1） |
| 存量预警 | 存量未使用组件持续标记为 warning | 全量 `audit:deadcode` | 弱（exit 0） |
| 季度清理 | 每季度集中清理一次僵尸组件 | 本 SOP + 人工确认 | 中（流程约束） |

## 2. 组件全生命周期管理

### 2.1 新增准入

新增组件必须满足以下 checklist，否则 gate:dev 将阻断提交：

**准入 Checklist：**

- [ ] 组件名遵循 PascalCase 命名规范，不与现有组件重名
- [ ] 组件放在正确的目录层级（atoms / molecules / organisms / templates）
- [ ] 至少有一个业务模块明确使用该组件（consumers 承诺）
- [ ] 包含基本的 props 类型定义
- [ ] 如有必要，添加单元测试（`.test.tsx`）
- [ ] 在对应的 barrel 文件（`index.ts`）中导出（如适用）

**consumers 承诺规则：**

- 新增组件时，必须至少有一个调用方（业务页面/父组件）已经 import 该组件
- `gate:dev` 中的 `audit:deadcode --staged` 会自动验证：暂存区中的新组件如果零引用，将触发 violation
- 纯共享/通用组件也需要先有一个消费者，不允许"先放着以后用"

### 2.2 活跃维护

处于活跃状态的组件应满足：

- 引用次数 ≥ 1（由 `audit:deadcode` 的 `componentRefCounts` 字段追踪）
- 有对应的测试覆盖（复杂组件建议有测试）
- 随业务迭代同步更新

**定期检查：**

- 每周关注 `audit:deadcode` 报告中的「低引用组件 Top 10」
- 引用次数 = 1 的组件属于"濒临僵尸"状态，应重点关注
- 若唯一消费者即将废弃，需提前规划组件的迁移或删除

### 2.3 观察预警

满足以下任一条件的组件进入**观察列表**：

- 连续 2 个迭代（约 4 周）引用数为 0
- 引用次数 = 1 且唯一消费者标记为 deprecated
- 组件功能被新组件替代，但旧组件尚未删除

**观察列表管理：**

- 在组件文件顶部添加注释标记：`// OBSERVE: 观察至 YYYY-MM-DD，原因：xxx`
- 观察期为 1 个季度
- 观察期内如果恢复引用，移除观察标记
- 观察期结束仍无引用 → 进入废弃流程

### 2.4 废弃流程

组件废弃遵循以下五步流程：

```
标记 deprecated → 通知相关方 → 迁移替代方案 → 归档 → 删除
```

**Step 1：标记 deprecated**

在组件文件顶部添加 JSDoc 注释：

```tsx
/**
 * @deprecated 自 vX.Y.Z 起废弃，请使用 NewComponent 替代
 * 计划删除日期：YYYY-MM-DD
 * 废弃原因：功能被 NewComponent 统一替代
 */
export function OldComponent() {
  // ...
}
```

同时在组件名后追加 `_deprecated` 后缀（可选，用于强提醒）。

**Step 2：通知相关方**

- 在团队周会上宣布废弃计划
- 通知可能使用该组件的模块负责人
- 在 CHANGELOG 中记录废弃项

**Step 3：迁移替代方案**

- 提供迁移指南：旧组件 → 新组件的映射关系
- 如有自动化 codemod，提供脚本
- 迁移窗口期：至少 1 个迭代

**Step 4：归档**

- 将组件移动到 `src/components/_deprecated/` 目录
- 保留至少 1 个季度的归档期
- 归档期内如有紧急回退需求，可快速恢复

**Step 5：删除**

- 归档期结束后，确认无新增引用
- 执行删除并提交
- 在 CHANGELOG 中记录

### 2.5 季度清理节奏

每季度按以下时间节奏执行清理：

| 阶段 | 时间 | 动作 | 负责人 |
|------|------|------|--------|
| 审计期 | 季度首月第 1 周 | 运行全量审计，生成待清理清单 | 架构负责人 |
| 确认期 | 季度首月第 2-3 周 | 分配给模块负责人，确认废弃/保留 | 模块负责人 |
| 标记期 | 季度首月第 4 周 | 批量标记 deprecated，添加观察标记 | 架构负责人 + 模块负责人 |
| 验证期 | 季度中月 | 运行审计验证无新增引用，推进迁移 | 各模块负责人 |
| 清理期 | 季度末月 | 执行删除，提交清理 PR | 架构负责人 |

## 3. 季度清理操作步骤

### 3.1 Step 1：全量审计获取未使用组件清单

```bash
# 运行死代码审计，输出 JSON 报告
npm run audit:deadcode

# 查看最新的审计报告（路径以实际输出为准）
# 报告位置：docs/reports/audit/audit-dead-code-{timestamp}.json
```

重点关注报告中的以下字段：

- `summary.unusedComponents`：未使用组件总数
- `summary.componentRefCounts`：所有组件的引用次数映射表
- `issues[].type === '未使用组件'`：零引用组件列表
- `issues[].refCount`：每个未使用组件的引用次数

### 3.2 Step 2：检查注册表现状

```bash
# 运行注册表审计，确认动态注册组件
npm run audit:registry
```

**注意：** 以下类型的组件即使零引用也不算僵尸组件：

- 通过 `widgetRegistry` 动态注册的组件（agent 组件等）
- 通过 MCP 服务端渲染的组件
- 作为插件/扩展点注册的组件

这些组件应从待清理清单中排除。

### 3.3 Step 3：生成待清理清单并分配

根据审计结果，生成 `待清理组件清单`，格式如下：

| 组件路径 | 引用次数 | 所属模块 | 负责人 | 状态 | 计划动作 |
|----------|----------|----------|--------|------|----------|
| src/components/atoms/OldButton.tsx | 0 | atoms | 张三 | 观察中 | 标记 deprecated |
| src/components/molecules/OldCard.tsx | 1 | molecules | 李四 | 濒临僵尸 | 确认是否保留 |

分配原则：

- 按组件目录归属分配给对应模块负责人
- 归属不明确的组件由架构负责人认领
- 每个待清理项必须有明确的负责人

### 3.4 Step 4：负责人确认并标记

模块负责人对分配的待清理项进行确认：

- **确认废弃**：在组件上添加 `@deprecated` 标记，计划下季度删除
- **确认保留**：补充使用方或文档说明，并在审计中排除（如动态注册组件）
- **需要观察**：添加观察标记，延长 1 个季度

确认完成后，将结果反馈给架构负责人。

### 3.5 Step 5：下季度末验证并删除

下季度末执行：

1. 重新运行 `npm run audit:deadcode`
2. 验证已标记 deprecated 的组件仍无新增引用
3. 确认无回退需求
4. 执行删除并提交 PR
5. 在 CHANGELOG 中记录删除项

## 4. 僵尸组件判定标准

### 4.1 核心判定条件

一个组件被判定为"僵尸组件"，需**同时满足**以下条件：

1. **零业务引用**：在排除测试文件、barrel 自身引用后，无业务代码引用
2. **非动态注册**：不是通过 registry、MCP、插件机制等方式动态加载的组件
3. **持续未使用**：连续 2 个迭代（约 4 周）未被新增引用

### 4.2 排除清单

以下组件即使零引用也**不**视为僵尸组件：

| 类型 | 说明 | 判定方式 |
|------|------|----------|
| 动态注册组件 | 通过 widgetRegistry / agentRegistry 等注册的组件 | audit:registry 中存在记录 |
| MCP 渲染组件 | 由 MCP 服务端动态渲染的组件 | 组件目录包含 mcp/ 或有相关注释 |
| 基础样式组件 | 纯 CSS/样式包装组件，通过 className 间接使用 | 需人工确认 |
| 开发/调试组件 | 仅在开发环境使用的组件（如 DevTools） | 文件名含 .dev 或有 DEV_ONLY 标记 |
| 新创建组件 | 刚创建尚未接入业务的组件（观察期内） | git log 显示创建时间 < 2 周 |

### 4.3 引用次数分级

| 引用次数 | 级别 | 说明 | 动作 |
|----------|------|------|------|
| 0 | 僵尸 | 完全未被使用 | 进入废弃流程 |
| 1 | 濒临僵尸 | 只有一个消费者 | 重点关注，评估是否合并 |
| 2-5 | 正常 | 有稳定的使用方 | 正常维护 |
| > 5 | 核心 | 被广泛使用 | 重点维护，确保质量 |

## 5. 工具与命令速查

| 命令 | 用途 | 退出码 |
|------|------|--------|
| `npm run audit:deadcode` | 全量死代码审计 | 0=仅warning, 1=有violation |
| `npm run audit:deadcode -- --staged` | 增量零容忍审计（暂存区） | 0=通过, 1=暂存区有零引用组件 |
| `npm run audit:deadcode -- --diff` | 同上（--staged 的别名） | 同上 |
| `npm run audit:registry` | 注册表审计 | 视配置而定 |
| `npm run audit:componentUsage` | 组件使用情况审计 | 视配置而定 |
| `npm run gate:dev` | 开发门禁（含增量死代码检查） | 0=通过, 1=阻断 |
| `npm run gate:quick` | 快速门禁（含增量死代码检查） | 0=通过, 1=阻断 |
