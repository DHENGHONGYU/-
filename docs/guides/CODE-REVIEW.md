# code-review.md — V9 代码审查标准与流程

> **Version**: v1.0.0 | **日期**: 2026-07-05
> **适用范围**: 所有人工代码审查（PR Review、Pair Review、Architecture Review）
> **强制等级**: P0 问题必须修复后才能合并

---

## 一、代码审查层级体系

### 1.1 三级审查体系

```
┌─────────────────────────────────────────────────────────┐
│  L1: 自动化审查（强制）                                │
│  ├── ESLint 自动修复 + 检查                           │
│  ├── TypeScript 类型检查                              │
│  ├── 单元测试（覆盖率 > 80%）                         │
│  ├── 架构审计（audit:layers/hardcode/deadcode）       │
│  └── Husky + lint-staged 提交前检查                   │
└─────────────────────────────────────────────────────────┘
                         ↓ 自动通过
┌─────────────────────────────────────────────────────────┐
│  L2: 同级审查（ mandatory）                            │
│  ├── 所有业务代码必须至少 1 人审查                    │
│  ├── 核心模块（services/store/core）必须 2 人审查    │
│  └── 审查者使用本章检查清单                           │
└─────────────────────────────────────────────────────────┘
                         ↓ 审查通过
┌─────────────────────────────────────────────────────────┐
│  L3: 架构审查（特定场景）                              │
│  ├── 跨模块重构（3+ 模块）                            │
│  ├── 数据库 Schema 变更                                │
│  ├── 接口签名变更                                      │
│  └── 技术栈变更（需技术评审委员会）                    │
└─────────────────────────────────────────────────────────┘
```

### 1.2 审查角色定义

| 角色 | 职责 | 权限 |
|------|------|------|
| **Author（作者）** | 编写代码、响应审查意见、修复问题 | 创建 PR、响应意见 |
| **Reviewer（审查者）** | 检查代码质量、提出改进建议、批准/拒绝 PR | 批准/拒绝 PR、请求修改 |
| **Architect（架构师）** | 审查架构影响、技术决策合规性 | 否决架构违规 PR |
| **Maintainer（维护者）** | 最终合并权限、版本发布决策 | 合并 PR、管理分支 |

## 二、代码审查标准（Checklist）

### 2.1 强制检查项（P0 - 必须修复）

#### ? 架构合规性

- [ ] **分层规则**: 无跨层调用违规（通过 `npm run audit:layers`）
- [ ] **依赖方向**: import 路径符合 AGENTS.md §1 依赖方向规则
- [ ] **四步集成**: 新模块按类型定义 → Store → Service → UI 顺序集成
- [ ] **路由注册**: 新增页面在 `routes.ts` + App 分发器 + `../explanation/06-routing-specs.md` 三处同步更新

#### ? 类型安全

- [ ] **无 any 类型**: 未使用 `any`（ESLint `@typescript-eslint/no-explicit-any: error`）
- [ ] **无 ts-ignore**: 未使用 `@ts-ignore`（使用 `@ts-expect-error` + 注释）
- [ ] **Interface 定义**: 所有数据结构有 TypeScript Interface
- [ ] **类型测试**: 复杂泛型有 `Expect<Equals>` 测试（位于 `tests/__tests__/types/`）

#### ? 零硬编码

- [ ] **颜色令牌**: 未直接使用 HEX 或 Tailwind 颜色类（通过 `npm run audit:hardcode`）
- [ ] **魔法数字**: 3位以上数字已提取为 const 或 config
- [ ] **配置注入**: 引擎层阈值/权重/公式参数从 `config.ts` 注入

#### ? 功能正确性

- [ ] **单元测试**: 新增代码有对应单元测试（覆盖率 > 80%）
- [ ] **边界处理**: 处理了 null/undefined/empty 等边界情况
- [ ] **错误处理**: 异步操作有 try-catch 和错误日志
- [ ] **事件清理**: useEffect 中的事件监听有 cleanup（参考 AGENTS.md §3 模板）

### 2.2 推荐检查项（P1 - 强烈建议）

#### ?? 代码质量

- [ ] **命名规范**: 变量/函数/组件命名清晰、符合约定（AGENTS.md §4）
- [ ] **函数长度**: 单个函数 < 50 行（超过需拆分）
- [ ] **文件长度**: 单个文件 < 300 行（超过需拆分）
- [ ] **复杂度**: 圈复杂度 < 10（通过 ESLint `complexity` 规则）
- [ ] **重复代码**: 无复制粘贴代码（提取为公共函数）

#### ?? 性能优化

- [ ] **避免不必要的重渲染**: React 组件使用 `React.memo` / `useMemo` / `useCallback`
- [ ] **懒加载**: 大型组件使用 `React.lazy()` 或动态 import
- [ ] **防抖节流**: 搜索/滚动等高频操作有防抖/节流
- [ ] **内存泄漏**: 定时器/订阅在组件卸载时清理

#### ?? 可维护性

- [ ] **注释清晰**: 复杂逻辑有 JSDoc 注释
- [ ] **日志规范**: 核心分支有 `logger.info` 打印（格式：`[模块名] 操作名`）
- [ ] **文档同步**: 类型定义变更同步更新 `../explanation/06-routing-specs.md` 或数据字典
- [ ] **TODO/FIXME**: 临时方案有 JSDoc 注释说明原因和后续计划

### 2.3 可选检查项（P2 - 建议改进）

#### 代码风格

- [ ] **一致性**: 代码风格与项目现有代码一致
- [ ] **简化代码**: 可以用更简洁方式实现（如数组方法替代循环）
- [ ] **类型推导**: 可以利用 TypeScript 类型推导减少冗余类型注解

#### 最佳实践

- [ ] **React 最佳实践**: 避免内联对象/函数定义（导致不必要的重渲染）
- [ ] **Zustand 最佳实践**: 使用 shallow 比较避免不必要的订阅触发
- [ ] **Tailwind 最佳实践**: 提取重复的类名为变量或使用 `cn()` 函数

## 三、代码审查流程

### 3.1 标准流程（适用于大多数场景）

```
┌──────────────────────────────────────────────────────────┐
│ Step 1: 作者自检（Pre-Review）                          │
├──────────────────────────────────────────────────────────┤
│ 1. 运行本地检查命令（见 §3.3）                          │
│ 2. 填写 PR 描述模板（见 §4.1）                          │
│ 3. 自查 Checklist（§2）                                  │
│ 4. 提交 PR 并指定审查者                                 │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│ Step 2: 审查者审查（Review）                             │
├──────────────────────────────────────────────────────────┤
│ 1. 检查 PR 描述完整性                                   │
│ 2. 运行本地验证命令（确保可复现）                        │
│ 3. 按 Checklist（§2）逐项检查                            │
│ 4. 使用审查意见模板（§4.2）提出意见                     │
│ 5. 批准（Approve）/ 请求修改（Request Changes）           │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│ Step 3: 作者修改（Revision）                             │
├──────────────────────────────────────────────────────────┤
│ 1. 响应所有审查意见                                      │
│ 2. 修改代码并回复审查意见                                │
│ 3. 重新提交审查（如需要）                                │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│ Step 4: 最终批准与合并（Approval & Merge）                │
├──────────────────────────────────────────────────────────┤
│ 1. 所有 P0 问题解决                                     │
│ 2. 审查者批准（Approved）                                │
│ 3. 维护者合并到主分支                                    │
│ 4. 删除功能分支（如适用）                                │
└──────────────────────────────────────────────────────────┘
```

### 3.2 快速流程（适用于简单场景）

**适用场景**：
- 文档更新（*.md 文件）
- 纯样式调整（CSS/Tailwind 类）
- 重构（不改变功能的代码整理）

**简化流程**：
1. 作者提交 PR（标注 `[SKIP_REVIEW]` 或 `[DOCS_ONLY]`）
2. 自动检查通过（ESLint + TypeScript + 单元测试）
3. 维护者直接合并（无需人工审查）

### 3.3 本地验证命令（作者/审查者）

```powershell
# 完整验证（提交前必须全部通过）
npm run lint              # ESLint 检查
npx tsc --noEmit         # TypeScript 类型检查
npm test -- --run         # 单元测试
npm run build             # 生产构建

# 架构审计（提交前必须 0 violations）
npm run audit:layers      # 分层调用检查
npm run audit:hardcode    # 硬编码检查
npm run audit:deadcode    # 死代码检查
npm run audit:docs        # 文档同步检查

# 可选：E2E 测试（影响 UI 的变更）
npm run test:e2e
```

## 五、审查者指南

### 5.1 审查者职责

1. **及时响应**: 在 24 小时内开始审查（工作日）
2. **全面检查**: 按 Checklist（§2）逐项检查，不遗漏
3. **建设性反馈**: 指出问题 + 提供修复建议（不只有批评）
4. **区分优先级**: 明确标注 P0/P1/P2 问题
5. **批准标准**: 所有 P0 问题解决后才能批准

### 5.2 审查者权限

| 操作 | 条件 | 说明 |
|------|------|------|
| **Approve** | 所有 P0 问题已解决 | 可以合并 |
| **Request Changes** | 存在 P0 或 P1 问题 | 作者需修改后重新提交 |
| **Comment** | 有疑问或 P2 建议 | 不阻塞合并，但作者应回应 |

### 5.3 审查重点（按模块类型）

#### 核心模块（`src/core/`, `src/services/`, `src/store/`）

- ? **必须 2 人审查**
- ? **重点检查**: 架构合规性、类型安全、性能、错误处理
- ? **必须**: 单元测试（覆盖率 > 90%）

#### UI 组件（`src/components/`, `src/pages/`）

- ? **必须 1 人审查**
- ? **重点检查**: 颜色令牌、事件清理、性能优化（重渲染）
- ? **推荐**: E2E 测试（涉及关键流程）

#### 配置文件（`src/config/`, `src/constants/`）

- ? **必须 1 人审查**（最好是架构师）
- ? **重点检查**: 命名规范、注释清晰、无硬编码

## 六、常见问题与最佳实践

### 6.1 如何处理审查意见分歧？

1. **先沟通**: 作者与审查者先讨论（评论区或线下）
2. **查文档**: 以 AGENTS.md 和本文档为准
3. **升级**: 无法达成一致时，请架构师仲裁
4. **记录**: 重要决策记录到 `docs/changelogs/YYYY-MM/`

### 6.2 如何平衡审查严格度与开发速度？

**原则**: P0 问题零容忍，P1 问题灵活处理，P2 问题记录跟进

- **紧急修复（Hotfix）**: 可先合并，但需在 24 小时内补充审查和测试
- **常规开发**: 严格执行 Checklist，不降低标准
- **技术债**: P1/P2 问题记录到 Issue，后续迭代修复

### 6.3 如何提高审查效率？

**作者侧**:
- 提交前先自查（减少往返次数）
- PR 尽量小（< 500 行），避免大 PR
- 写清晰的 PR 描述（帮助审查者理解）

**审查者侧**:
- 使用 ESLint/TypeScript 自动检查工具（减少人工检查）
- 优先检查架构/类型/安全（高价值），其次代码风格（低价值）
- 批量审查（避免频繁切换上下文）
