# 踩坑规则门禁指南

> **Status**: Current
> **Version**: v1.0.0
> **Last Updated**: 2026-07-03
>
> 本文档介绍 V9 项目的踩坑规则门禁体系（规则 #11-#14），包括规则定义、本地拦截机制、远程 CI/CD 拦截机制。
> 目标读者：所有提交代码的开发者，特别是团队新人。

---

## 1. 概述

踩坑规则门禁是一套自动化代码检查机制，用于在代码提交阶段拦截 4 类高频踩坑问题。门禁体系采用**本地 + 远程双重拦截**架构：

| 拦截层 | 触发时机 | 检查工具 | 拦截行为 |
|--------|----------|----------|----------|
| **本地 husky pre-commit** | `git commit` | `scripts/pitfall_check.py` | exit 1 阻止提交 |
| **远程 CI/CD 流水线** | `push` / `PR` 到 main/develop | `scripts/pitfall_check.py` | exit 1 阻止流水线 |

新人只需记住：**提交代码前，门禁会自动检查；违规代码无法提交**。

---

## 2. 门禁体系架构

### 2.1 本地拦截链路（husky 9.x）

```
git commit
  → core.hooksPath = .husky/_
  → .husky/_/pre-commit (husky 包装器)
  → husky h 脚本
  → .husky/pre-commit (用户脚本)
     ├─ npx lint-staged          (ESLint 修复 .ts/.tsx 文件)
     └─ python scripts/pitfall_check.py   (踩坑规则检查)
         └─ exit 1 if ERROR       (阻止提交)
```

### 2.2 远程拦截链路（GitHub Actions）

```
git push origin main
  → GitHub Actions 触发 quality-check.yml
  → Checkout + Setup Node.js + Setup Python 3.11
  → TypeScript compilation
  → JSON validation
  → ESLint check
  → Pitfall rules check           (踩坑规则检查)
     └─ python scripts/pitfall_check.py python/ scripts/
     └─ exit 1 if ERROR            (阻止流水线)
  → Unit tests
  → Data blueprint validation
```

### 2.3 检查范围

| 拦截层 | 检查范围 | 说明 |
|--------|----------|------|
| 本地 husky | git 暂存区文件 | 只检查本次提交的文件 |
| 远程 CI/CD | `python/` + `scripts/` 目录 | 检查所有 Python 代码 |

## 3. 四条规则详解

### 规则 #11: 正则动态构造

| 属性 | 值 |
|------|-----|
| **严重级别** | ERROR（JS/TS）/ WARN（Python）|
| **首次发现** | V9 2026-07-03 |
| **检查器** | `check_regex_dynamic_construction` |

**问题描述**：JavaScript 字面量正则 `/v_${var}=/` 中的 `${var}` 不会插值，被当作字面字符串，导致正则匹配静默失败。

**根因**：JS 字面量正则 `/.../` 不支持模板字符串插值，必须用 `new RegExp()` 构造。

**铁律**：动态正则必须用 `new RegExp()` 构造，禁止在字面量正则中使用 `${var}`。

**违规示例（JS/TS）**：

```javascript
// ❌ 违规：字面量正则中 ${tencentCode} 不插值
const match = data.match(/v_${tencentCode}="([^"]+)"/);
```

**修复示例（JS/TS）**：

```javascript
// ✅ 正确：用 new RegExp() 构造动态正则
const match = data.match(new RegExp(`v_${tencentCode}="([^"]+)"`));
```

**Python 注意事项**：

```python
# ❌ 违规：re.compile 中的 ${} 不是插值语法
pattern = re.compile("v_${var}=")

# ✅ 正确：使用 f-string
pattern = re.compile(f"v_{var}=")
```

### 规则 #12: 第三方库调用超时

| 属性 | 值 |
|------|-----|
| **严重级别** | ERROR（requests）/ WARN（AKShare）|
| **首次发现** | V9 2026-07-03 |
| **检查器** | `check_timeout_control` |

**问题描述**：`requests.get()` 无 `timeout` 参数，或 AKShare 函数直接调用无超时包装，会导致程序无限等待，最终 TIMEOUT。

**根因**：`requests` 库默认无超时；AKShare 内部不支持 `timeout` 参数。

**铁律**：
- `requests` 调用必须设置 `timeout` 参数
- AKShare 调用必须用 `call_with_timeout` 包装

**违规示例**：

```python
# ❌ 违规：requests.get 无 timeout
response = requests.get("https://example.com")

# ❌ 违规：AKShare 直接调用无超时包装
df = ak.stock_zh_a_spot_em()
```

**修复示例**：

```python
# ✅ 正确：requests 设置 timeout
response = requests.get("https://example.com", timeout=8.0)

# ✅ 正确：AKShare 用 call_with_timeout 包装
from lib.timeout_utils import call_with_timeout

df = call_with_timeout(ak.stock_zh_a_spot_em, timeout=8.0)
```

**需要超时控制的函数列表**（定义于 `scripts/pitfall_check.py`）：

```
stock_zh_a_spot_em, stock_zh_a_daily, stock_individual_info_em,
stock_financial_em, requests.get, requests.post, requests.put,
requests.delete, urlopen
```

### 规则 #13: TTL+LRU 缓存

| 属性 | 值 |
|------|-----|
| **严重级别** | WARN |
| **首次发现** | V9 2026-07-03 |
| **检查器** | `check_cache_strategy` |

**问题描述**：频繁调用的外部 API（如全市场行情）无缓存机制，导致重复请求、延迟累积。

**根因**：无缓存策略，每次调用都发起网络请求。

**铁律**：频繁调用的 API 必须有 TTL+LRU 缓存。

**违规示例**：

```python
# ❌ 违规：文件中调用 stock_zh_a_spot_em 但无任何缓存机制
def fetch_quote(symbol):
    df = ak.stock_zh_a_spot_em()  # 每次都拉取全市场行情
    return df[df['代码'] == symbol]
```

**修复示例**：

```python
# ✅ 正确：使用 TTL_LRUCache 或 @cached 装饰器
from lib.cache_utils import TTL_LRUCache

_spot_cache = TTL_LRUCache(capacity=100, ttl=300.0)  # 5分钟 TTL

def fetch_quote(symbol):
    df = _spot_cache.get('spot_em', lambda: ak.stock_zh_a_spot_em())
    return df[df['代码'] == symbol]
```

**缓存标识**（检查器识别以下标识表示已缓存）：

```
@cached, TTL_LRUCache, _KLINE_CACHE, _SPOT_CACHE, call_with_cache, CachedAPIClient
```

**推荐缓存参数**：

| 数据类型 | TTL | LRU 容量 |
|----------|-----|----------|
| K线数据 | 10 分钟（600s） | 100 项 |
| 实时行情 | 5 分钟（300s） | 100 项 |
| 财务指标 | 30 分钟（1800s） | 50 项 |

### 规则 #14: 降级路径限制

| 属性 | 值 |
|------|-----|
| **严重级别** | WARN |
| **首次发现** | V9 2026-07-03 |
| **检查器** | `check_degradation_depth` |

**问题描述**：多层降级 + 每层重试 = 延迟累积。例如 3 层降级 × 2 次重试 × 指数退避 = 最坏 35 秒。

**根因**：降级路径过深，每层都有重试和退避，延迟线性叠加。

**铁律**：降级路径 ≤ 2 层，部分可用优于完全不可用。

**违规示例**：

```python
# ❌ 违规：3 层降级，每层重试 2 次，最坏 35 秒
def fetch_data(code):
    try:
        return ak.stock_individual_info_em(code)   # 第1层
    except:
        try:
            return ak.stock_zh_a_spot_em()          # 第2层
        except:
            try:
                return ak.stock_financial_em(code)  # 第3层 ← 过深
            except:
                return None
```

**修复示例**：

```python
# ✅ 正确：2 层降级，部分可用优于完全不可用
def fetch_data(code):
    try:
        return ak.stock_zh_a_spot_em()  # 唯一数据源（含 5min 缓存）
    except Exception as e:
        logger.warning("行情获取失败: %s", e)
        return {'price': None, 'pe': None}  # 降级返回 None，不阻塞
```

**检查阈值**（触发 WARN）：

- 文件中出现 `第3层` / `第4层` / `第3层降级` 等关键词
- 文件中 `try:` 块 ≥ 3 个 **且** `except` 块 ≥ 4 个

## 4. 本地拦截：husky pre-commit

### 4.1 配置文件

| 文件 | 作用 |
|------|------|
| [.husky/pre-commit](../.husky/pre-commit) | 用户脚本，调用 lint-staged + pitfall_check.py |
| [.husky/_/pre-commit](../.husky/_/pre-commit) | husky 包装器（自动生成，勿手动修改）|
| [package.json](../package.json) | `"prepare": "husky"` 初始化 husky |

### 4.2 pre-commit 脚本内容

```bash
npx lint-staged

# 踩坑规则门禁检查（v2.1 修复同步）
python scripts/pitfall_check.py
if [ $? -ne 0 ]; then
  echo "❌ 踩坑规则门禁检查未通过，已阻止提交"
  exit 1
fi
```

### 4.3 跳过门禁（不推荐）

```bash
git commit --no-verify -m "..."
```

> ⚠️ **警告**：跳过本地门禁后，CI/CD 仍会在远程拦截。不要养成跳过门禁的习惯。

## 6. 使用方式

### 6.1 日常提交（自动触发）

```bash
git add .
git commit -m "feat: 新功能"
```

门禁会自动执行，违规时 commit 失败。根据提示修复后重新提交。

### 6.2 手动检查（提交前预检）

```bash
# 检查指定目录
python scripts/pitfall_check.py python/ scripts/

# 检查指定文件
python scripts/pitfall_check.py path/to/file.py

# 不传参数：检查 git 暂存区文件（与 husky 行为一致）
python scripts/pitfall_check.py
```

### 6.3 退出码说明

| 退出码 | 含义 |
|--------|------|
| 0 | 全部通过（允许提交）|
| 1 | 存在 ERROR 违规（阻止提交）|

> WARN 不阻止提交，仅作提示。

## 8. 常见问题

### Q1: 门禁报错但我认为不是违规，怎么办？

1. 检查是否为误报（如 docstring 内的代码片段被误检测）
2. 确认检查器逻辑：`scripts/pitfall_check.py` 第 157-349 行
3. 如确认为误报，可使用 `git commit --no-verify` 跳过（不推荐）

### Q2: husky 没有触发，commit 直接成功？

检查 husky 是否正确安装：

```bash
git config core.hooksPath
# 期望输出: .husky/_

ls .husky/_/pre-commit
# 期望文件存在
```

如未安装，运行 `npx husky` 重新初始化。

### Q3: CI/CD 流水线从未执行？

项目需要配置 GitHub 远程仓库：

```bash
git remote add origin https://github.com/<user>/<repo>.git
git push -u origin main
```

### Q4: 如何添加新的踩坑规则？

1. 在 `scripts/pitfall_check.py` 中添加新的检查器函数
2. 在 `CHECKERS` 列表中注册（第 356-361 行）
3. 在 [踩坑备忘录](../.trae/skills/ai-driven-app-development/prompts/踩坑备忘录.md) 中添加规则描述
4. 更新本文档

### Q5: pitfall_check.py 为什么不检查自身？

脚本内部的 `filter_code_lines` 函数用简单的 `marker in line` 检测 docstring，无法区分字符串字面量中的 `"""` 和真正的 docstring `"""`。为避免自指误报，`check_file` 函数（第 369-374 行）跳过自身文件。
