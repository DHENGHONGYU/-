# 质量保障策略：分阶段自适应检查机制

> **版本**: v1.0.0 | **日期**: 2026-07-12
> **适用范围**: V9 智能投研复盘系统全生命周期
> **核心目标**: 在不同开发阶段平衡质量控制与开发效率

---

## 一、策略背景

当前项目正处于高强度开发与测试阶段，后续检查力度预计将逐步降低。本策略旨在：

1. **明确不同阶段的检查重点和频率**
2. **调整自动化测试与人工审查的比例**
3. **制定关键节点的质量门禁标准**
4. **建立持续监控机制确保质量底线**

---

## 二、三阶段质量模型

### 2.1 阶段定义

| 阶段 | 名称 | 适用场景 | 自动检测条件 |
|------|------|---------|-------------|
| **intensive** | 高强度开发测试期 | 功能密集开发、架构重构、模块迁移 | 近7天 commit ≥ 30 |
| **normal** | 稳定维护期 | 功能稳定、常规迭代、Bug修复 | 近7天 commit 10-29 |
| **lightweight** | 低维护期 | 功能冻结、仅安全更新、长期维护 | 近7天 commit < 10 |

### 2.2 阶段切换机制

```
┌─────────────────────────────────────────────────────────────────┐
│                    阶段自动检测与切换                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   git log --oneline --since="7 days ago"                        │
│           │                                                     │
│           ▼                                                     │
│   commitCount ≥ 30 ? ──Yes──→ intensive (高强度开发测试期)       │
│           │                                                     │
│           No                                                    │
│           ▼                                                     │
│   commitCount ≥ 10 ? ──Yes──→ normal (稳定维护期)                │
│           │                                                     │
│           No                                                    │
│           ▼                                                     │
│           → lightweight (低维护期)                              │
│                                                                 │
│   手动覆盖: QUALITY_PHASE=intensive|normal|lightweight          │
│   命令覆盖: npx tsx scripts/system-check-loop.ts --phase=xxx    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 阶段切换判断标准

**从 intensive → normal 的条件**（满足任意两项）：
- 连续3周 commit 数 < 30
- 架构重构任务完成率 ≥ 90%
- 核心功能开发完成率 ≥ 95%
- 无 P0/P1 级阻塞性问题

**从 normal → lightweight 的条件**（满足任意两项）：
- 连续4周 commit 数 < 10
- 功能冻结声明已发布
- 仅进行安全更新和紧急修复
- 团队进入维护模式

**向上切换的条件**（任意触发）：
- 启动新的大型功能开发
- 进行架构升级或重构
- 发现严重质量问题需全面审查

### 3.3 检查重点对比

#### 高强度开发测试期（intensive）

**重点关注**：
- 架构合规性（分层调用、依赖方向）
- 代码质量（硬编码、死代码、颜色令牌）
- 文档同步（自动更新、保鲜度）
- 测试覆盖（覆盖率、新增测试）
- MCP架构（权限配置、ACL矩阵）

**资源配置**：
- 自动化: 85%
- 人工审查: 15%
- 每日检查周期: ~30分钟

#### 稳定维护期（normal）

**重点关注**：
- 核心架构合规性（分层调用、路由）
- 代码质量（硬编码、颜色令牌）
- 文档同步（基础验证）
- 系统健康度（综合评分）

**资源配置**：
- 自动化: 90%
- 人工审查: 10%
- 每3天检查周期: ~15分钟

#### 低维护期（lightweight）

**重点关注**：
- 核心防护（分层调用、硬编码、路由）
- 系统健康度（综合评分）
- 安全更新影响评估

**资源配置**：
- 自动化: 95%
- 人工审查: 5%
- 每周检查周期: ~5分钟

## 四、质量门禁标准

### 4.1 门禁阈值矩阵

| 指标 | intensive | normal | lightweight |
|------|-----------|--------|-------------|
| **综合评分** | ≥ 85 | ≥ 75 | ≥ 65 |
| **严重问题数** | ≤ 0 | ≤ 1 | ≤ 2 |
| **高优先级问题数** | ≤ 2 | ≤ 5 | ≤ 8 |
| **测试覆盖率** | ≥ 70% | ≥ 60% | ≥ 50% |
| **文档保鲜度** | ≥ 80% | ≥ 70% | ≥ 60% |

### 4.2 门禁检查流程

```
┌─────────────────────────────────────────────────────────────┐
│                     质量门禁检查流程                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   检查开始                                                   │
│       │                                                     │
│       ▼                                                     │
│   执行审计 → 生成报告                                        │
│       │                                                     │
│       ▼                                                     │
│   综合评分 ≥ 阶段阈值?                                       │
│       │                                                     │
│       ├── Yes ──→ 严重问题数 ≤ 阶段阈值?                     │
│       │                 │                                   │
│       │                 ├── Yes ──→ 高优先级问题数 ≤ 阈值?   │
│       │                 │                 │                 │
│       │                 │                 ├── Yes ──→ 通过  │
│       │                 │                 │                 │
│       │                 │                 └── No ──→ 警告  │
│       │                 │                                   │
│       │                 └── No ──→ 拒绝                     │
│       │                                                     │
│       └── No ──→ 拒绝                                       │
│                                                             │
│   通过 → 允许部署/合并                                        │
│   警告 → 需人工确认后允许                                     │
│   拒绝 → 必须修复后重试                                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 关键节点门禁

#### 代码合并门禁（PR Merge）

| 阶段 | 强制检查项 | 建议检查项 |
|------|-----------|-----------|
| intensive | lint、tsc、unit tests | audit:layers、audit:hardcode |
| normal | lint、tsc | unit tests |
| lightweight | lint | tsc |

#### 部署门禁（Deployment）

| 阶段 | 强制检查项 | 建议检查项 |
|------|-----------|-----------|
| intensive | 全量审计、质量评分 | E2E测试 |
| normal | 核心审计 | 健康度检查 |
| lightweight | 健康度检查 | - |

#### 版本发布门禁（Release）

| 阶段 | 强制检查项 | 建议检查项 |
|------|-----------|-----------|
| intensive | 全量审计、质量评分、E2E | 性能测试 |
| normal | 核心审计、健康度检查 | 回归测试 |
| lightweight | 健康度检查、安全扫描 | - |

## 五、自动化与人工审查比例

### 5.1 比例配置

| 阶段 | 自动化比例 | 人工审查比例 | 人工审查重点 |
|------|-----------|------------|-------------|
| **intensive** | 85% | 15% | 架构决策、复杂功能设计、核心算法 |
| **normal** | 90% | 10% | Bug修复验证、关键业务逻辑 |
| **lightweight** | 95% | 5% | 安全更新、紧急修复 |

### 5.2 自动化检查清单

**核心自动化检查**（始终运行）：
- 类型检查（tsc --noEmit）
- ESLint 代码规范
- 单元测试
- 分层调用审计（audit:layers）
- 硬编码检测（audit:hardcode）
- 路由验证（audit:routes）

**阶段自适应检查**：
- intensive: 全量审计 + 文档验证 + 测试覆盖率
- normal: 核心审计 + 文档验证
- lightweight: 核心审计

### 5.3 人工审查清单

**定期人工审查**：
- 架构评审（每2周，intensive期每周）
- 代码审查（PR级，intensive期严格）
- 文档审查（每季度）
- 安全审查（每季度）

**触发式人工审查**：
- 质量评分下降 > 10分
- 发现严重安全问题
- 架构变更影响评估

## 六、持续监控机制

### 6.1 监控指标体系

| 类别 | 指标 | 监控频率 | 告警阈值 |
|------|------|---------|---------|
| **代码质量** | 综合评分 | 每次检查 | < 阶段阈值 |
| **代码质量** | 严重问题数 | 每次检查 | > 阶段阈值 |
| **代码质量** | 高优先级问题数 | 每次检查 | > 阶段阈值 |
| **测试覆盖** | 测试覆盖率 | 每次检查 | < 阶段阈值 |
| **文档质量** | 文档保鲜度 | 每次检查 | < 阶段阈值 |
| **架构合规** | 跨层调用违规数 | 每次检查 | > 0（intensive） |
| **Token消耗** | 月度Token消耗 | 每月 | > 50,000/会话 |

### 6.2 告警机制

```
┌─────────────────────────────────────────────────────────────┐
│                       告警机制                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   检查结果                                                   │
│       │                                                     │
│       ▼                                                     │
│   质量门禁通过?                                              │
│       │                                                     │
│       ├── Yes ──→ 评分下降 > 10%? ──Yes──→ 警告通知         │
│       │                 │                                   │
│       │                 └── No ──→ 正常通过                  │
│       │                                                     │
│       └── No ──→ 创建GitHub Issue                          │
│                     │                                       │
│                     ├── 严重问题 → @团队负责人              │
│                     └── 一般问题 → @相关开发者              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 持续改进闭环

```
┌─────────────────────────────────────────────────────────────┐
│                    持续改进闭环                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   检查执行 → 问题发现 → 问题分类 → 修复跟踪 → 验证关闭        │
│       │                                                         │
│       └────────────────→ 统计分析 → 根因分析 → 流程优化       │
│                                                             │
│   输出: 每周质量报告、月度趋势分析、季度改进建议              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
