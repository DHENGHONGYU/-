## 一、背景与目标

本文档基于 NewsPage（智能资讯中心）PoC 迁移的实战经验，系统复盘 V6 → V9 迁移过程中 tRPC 到 DataBridge 适配的技术风险、实际踩坑记录及应对策略，为后续页面迁移提供可复用的决策依据。

## 二、风险矩阵总览

### 2.1 迁移前评估 vs 迁移后验证

| 风险点 | 迁移前评估 | 实际验证 | 偏差分析 |
|--------|-----------|----------|----------|
| tRPC → DataBridge | 🔴 **高风险** | 🟢 **低风险** | V6 NewsPage 实际未使用 tRPC，为纯前端 Mock，数据流重构风险被高估 |
| 状态管理转换 | 🔴 **高风险** | 🟢 **低风险** | NewsPage 使用本地 useState，无全局 Store 依赖，转换成本极低 |
| Widget 注册机制 | 🟡 **中风险** | 🟢 **低风险** | NewsPage 为独立页面，无 Widget 框架耦合 |
| 类型差异适配 | 🟡 **中风险** | 🟡 **中风险** | `sentiment` 字段从 `number` 到 `string enum` 的转换是真实工作量 |
| UI 骨架还原 | 🟢 **低风险** | 🟢 **低风险** | DOM 结构和 className 直接复制，视觉还原度高 |

### 2.2 关键发现

**最大偏差**：tRPC → DataBridge 的风险被显著高估。V6 项目中并非所有页面都使用 tRPC，部分页面（如 NewsPage）使用本地 Mock 数据或简单 fetch，这类页面的迁移难度远低于预期。

## 三、踩坑实录

### 3.1 🔴 类型差异陷阱（真实阻塞风险）

#### 问题描述
V6 与 V9 的 `NewsArticle` 类型在 `sentiment` 字段上存在本质差异：

```typescript
// V6 类型：sentiment 为 number（-1.0 ~ 1.0）
interface V6NewsArticle {
  sentiment: number          // 如 0.65 表示看多，-0.45 表示看空
  sentimentConfidence: number
}

// V9 类型：sentiment 为 string enum
interface V9NewsArticle {
  sentiment: 'positive' | 'negative' | 'neutral'
  sentimentConfidence: number
}
```

#### 影响范围
- **UI 渲染**：V6 的 `SentimentBadge` 组件基于数值判断（`> 0.3` 看多，`< -0.3` 看空），直接使用 V9 数据会导致所有情感标签显示为"中性"
- **筛选逻辑**：V6 的筛选面板按数值范围筛选，V9 数据无法匹配
- **排序功能**：按情感强度排序依赖数值绝对值

#### 踩坑过程
1. **第一次尝试**：直接传递 V9 数据给 V6 组件，发现情感标签全部失效
2. **第二次尝试**：在组件内部做类型判断，代码混乱且无法复用
3. **最终方案**：建立独立的**适配层**（`types.ts`），在数据进入 UI 前完成统一转换

#### 修复代码
```typescript
// src/pages/news-v6/types.ts
export function sentimentV9ToV6(
  sentiment: V9NewsArticle['sentiment'],
  confidence: number,
): number {
  const base = sentiment === 'positive' ? 0.6 : sentiment === 'negative' ? -0.6 : 0
  const variance = (confidence - 0.5) * 0.4
  return sentiment === 'positive'
    ? Math.min(0.99, base + variance)
    : sentiment === 'negative'
      ? Math.max(-0.99, base - variance)
      : 0
}

export function adaptV9ToV6(article: V9NewsArticle): V6NewsArticle {
  return {
    ...article,
    sentiment: sentimentV9ToV6(article.sentiment, article.sentimentConfidence),
  }
}
```

#### 经验总结
> **类型差异是迁移中最隐蔽的阻塞点**。表面上看两个类型"差不多"，但底层语义差异会导致 UI 完全失效。必须在迁移前建立完整的字段映射表，不能凭直觉判断兼容性。

### 3.2 🟡 Windows 大小写陷阱（构建阻断）

#### 问题描述
在 Windows 环境下，V6 源码使用小写导入路径，而 V9 项目使用 PascalCase：

```typescript
// V6 源码（在 Windows 上开发）
import { Card } from '@/components/ui/card'

// V9 项目规范
import { Card } from '@/components/ui/Card'
```

#### 报错信息
```
error TS1149: File name '.../src/components/ui/card.tsx' differs from 
already included file name '.../src/components/ui/Card.tsx' only in casing.
```

#### 踩坑过程
1. 直接复制 V6 源码到 V9 项目，本地运行正常（Windows 文件系统不区分大小写）
2. 运行 `tsc --noEmit` 时批量报错，所有 UI 组件导入路径均有问题
3. 需逐个文件修正导入路径大小写

#### 修复方式
批量替换导入路径为 PascalCase：
```typescript
// 修正后
import { Card, CardContent, CardHeader } from '@/components/ui/Card'
import { Badge } from '@/components/ui/Badge'
import { Button } from '@/components/ui/Button'
```

#### 经验总结
> **Windows 开发环境会掩盖大小写问题**。必须在迁移后立即运行 `tsc --noEmit`，不能依赖本地运行结果判断代码正确性。建议在迁移脚本中增加导入路径自动转换步骤。

### 3.3 🟡 组件选择器失效（测试脚本失败）

#### 问题描述
Playwright 测试脚本中最初使用 `[class*="Card"]` 选择器统计卡片数量，但 V6 迁移后的卡片组件使用了不同的 CSS 类名结构，导致选择器匹配失败。

#### 报错现象
```
❌ FAIL: 模拟数据生成成功 - 卡片数量: 0
```

实际上数据已正常加载，只是选择器无法定位到卡片元素。

#### 修复方式
将选择器从 CSS 类名改为更稳定的 DOM 结构选择器：
```javascript
// 失败的选择器
const cardCount = await page.locator('[class*="Card"]').count();

// 成功的选择器（基于 DOM 结构）
const titleCount = await page.locator('h3').count();
```

#### 经验总结
> **测试脚本的选择器必须与 V6 UI 结构对齐**。迁移后的测试不应使用 V9 组件的内部类名，而应基于 V6 的 DOM 结构（如 `h3` 标题、`button` 按钮等语义化标签）编写选择器，确保测试验证的是"V6 UI 是否正常工作"而非"V9 组件是否挂载"。

### 3.4 🟢 路由参数变化未刷新数据（预防性修复）

#### 问题描述
NewsPage 在 V6 中未使用路由参数，但在其他页面（如 StockAnalysisPage）中常见此问题：当 URL 参数变化时，页面数据未重新加载。

#### V6 原代码问题模式
```typescript
// ❌ 错误模式：只在 mount 时加载
useEffect(() => {
  loadData()
}, [])  // 空依赖，路由参数变化时不会刷新
```

#### V9 迁移时的预防性修复
```typescript
// ✅ 正确模式：依赖路由参数
const loadData = useCallback(async () => {
  // ...
}, [symbol])  // 依赖参数变化

useEffect(() => {
  loadData()
}, [loadData])  // 依赖 loadData
```

#### 经验总结
> **Page 组件必须处理路由参数变化**。虽然 NewsPage 本身不涉及此问题，但在迁移其他页面时，必须在 `useEffect` 依赖数组中包含路由参数，否则切换股票代码等操作不会触发数据刷新。

## 四、应对策略

### 4.1 类型差异应对策略

#### 策略一：强制适配层模式
**规则**：任何类型不兼容的字段，必须通过独立的适配函数转换，禁止在 UI 组件内部做类型判断。

```typescript
// ✅ 正确：集中式适配层
export function adaptV9ToV6(article: V9NewsArticle): V6NewsArticle { ... }

// ❌ 错误：分散在组件中
function SentimentBadge({ sentiment }: { sentiment: string | number }) {
  // 在组件内部判断类型，导致代码混乱
}
```

#### 策略二：字段映射表
迁移前必须输出字段差异对照表：

| 字段 | V6 类型 | V9 类型 | 是否需适配 | 适配函数 |
|------|---------|---------|-----------|----------|
| sentiment | `number` | `string enum` | ✅ 是 | `sentimentV9ToV6` |
| stockCode | `string` | `symbol: string` | ❌ 否 | 直接兼容 |
| source | `string` | `string` | ❌ 否 | 直接兼容 |

#### 策略三：双向转换函数
适配层必须提供双向转换，确保数据回写时格式正确：
```typescript
export function adaptV9ToV6(article: V9NewsArticle): V6NewsArticle { ... }
export function adaptV6ToV9(article: V6NewsArticle): V9NewsArticle { ... }
```

---

### 4.2 大小写兼容性应对策略

#### 策略一：导入路径规范化脚本
在迁移脚本中增加自动转换步骤：
```bash
# 自动将 @/components/ui/xxx 转换为 PascalCase
sed -i 's|@/components/ui/\([a-z]\)|@/components/ui/\u\1|g' src/pages/**/*.tsx
```

#### 策略二：IDE 自动修复
利用 VS Code 的 "Update Imports" 功能，批量修正导入路径。

#### 策略三：构建前置检查
将 `tsc --noEmit` 作为 CI 的第一步，确保大小写问题在合并前被发现。

### 4.3 测试脚本稳定性策略

#### 策略一：基于语义的选择器
测试脚本优先使用语义化标签，而非 CSS 类名：
```javascript
// ✅ 稳定的选择器
const title = page.locator('h3').first()
const button = page.locator('button:has-text("刷新")')

// ❌ 不稳定的选择器
const card = page.locator('[class*="Card"]')
```

#### 策略二：截图比对兜底
对于视觉验证，采用截图比对作为功能测试的补充：
```javascript
await page.screenshot({ path: 'baseline.png' })
// 后续运行对比差异
```

#### 策略三：数据无关的断言
断言应验证"行为"而非"具体数据"：
```javascript
// ✅ 验证行为
expect(await page.locator('h3').count()).toBeGreaterThan(0)

// ❌ 验证具体数据（易因 mock 数据变化而失败）
expect(await page.locator('text=贵州茅台').count()).toBe(1)
```

### 4.4 tRPC → DataBridge 通用适配策略

#### 场景一：V6 使用 tRPC.useQuery()
对于真实使用 tRPC 的页面，建议封装为 V9 Service 调用：

```typescript
// V6 原代码
const { data, isLoading } = trpc.news.getList.useQuery({ limit: 20 })

// V9 迁移后：封装为 Service 函数
const [articles, setArticles] = useState<NewsArticle[]>([])
const [loading, setLoading] = useState(false)

useEffect(() => {
  listNews({ limit: 20 }).then(result => {
    if (result.success) setArticles(result.data || [])
  })
}, [])
```

#### 场景二：V6 使用 fetch/axios
直接替换为 V9 `dataLayer` 或 `newsService` 调用，禁止保留直接 API 调用：

```typescript
// ❌ 禁止保留
const res = await fetch('/api/news')

// ✅ 必须替换
const result = await listNews({ limit: 20 })
```

#### 场景三：V6 使用本地 Mock
保留 Mock 生成器，但输出必须经过 V9 Service 层持久化：

```typescript
// V9 迁移后
const handleGenerateMock = async () => {
  const mockArticles = generateMockArticles(15)
  await saveNewsArticles(mockArticles)  // 通过 V9 Service 保存
  await loadNews()  // 再从 V9 读取
}
```

## 五、风险降级建议

基于 NewsPage PoC 经验，建议对后续页面的风险评级进行动态调整：

### 5.1 重新评估矩阵

| 页面特征 | 原风险等级 | 建议风险等级 | 工期估算 |
|----------|-----------|-------------|----------|
| 纯展示页（无 tRPC/无全局 Store） | 🔴 高 | 🟢 低 | 0.5-1 天 |
| 简单 CRUD 页（有 tRPC） | 🔴 高 | 🟡 中 | 1-2 天 |
| 复杂交互页（多状态/多筛选） | 🔴 高 | 🟡 中 | 2-3 天 |
| 依赖全局 Store 的页面 | 🔴 高 | 🔴 高 | 3-5 天 |
| 含 Widget 的 Dashboard | 🔴 高 | 🔴 高 | 5-7 天 |

### 5.2 快速评估清单

在启动单个页面迁移前，用以下清单快速评估真实风险：

- [ ] 该页面是否使用 `trpc.*.useQuery/useMutation`？
- [ ] 该页面是否调用 `useStockStore/useGlobalStore`？
- [ ] 该页面是否包含 `<Widget ...>` 或 `WidgetRegistry`？
- [ ] 该页面是否有自定义 Hook 依赖 V6 基础设施？
- [ ] 该页面的类型定义与 V9 差异是否超过 3 个字段？

**评分规则**：
- 0 项勾选 → 🟢 低风险（0.5-1 天）
- 1-2 项勾选 → 🟡 中风险（1-3 天）
- 3 项以上勾选 → 🔴 高风险（3-5 天，需专项方案）
