# 2026-08-12 会话复盘：工作树反复回退与并发环境下的 Git 操作纪律

## 1. 事件回顾

在本次会话中，我们进行了以下任务：
1.  **P1 硬编码修复**：修复了 19 个 Major 级别的硬编码问题（颜色、魔法数字），使 `audit:hardcode` 全绿。
2.  **MCP 架构债务分析**：分析了 13 条预存的 `direct-service-import` 违规，并生成了详细的修复方案文档。
3.  **团队操作指南更新**：在 `docs/guides/team-handbook/06-team-operation-guide.md` 中新增了 **6.4 防止工作树回退与安全提交** 一节。

然而，在执行过程中，我们遭遇了**严重的工作树回退问题**。具体表现为：
*   已修改的文件内容（如 P1 修复代码、MCP 方案文档、团队指南）在未被提交的情况下，**突然被清空或回退到了旧版本**。
*   多次尝试重新编辑文件，均会在不久后再次被回退。
*   Git 操作频繁被 `.git/index.lock` 阻塞。

## 2. 根因分析

经过排查，工作树回退的根本原因是**本地环境中存在多个并发运行的 Git/Node 进程**。

*   **并发进程干扰**：后台有多个 `node.exe` 进程（可能是由 IDE 插件、未关闭的脚本或系统级的守护任务启动的）在频繁地执行 Git 操作，如 `git status`、`git pull`、`git reset` 等。
*   **未提交的脆弱性**：我们在工作树中修改的文件（特别是尚未 commit 的文件）是“脆弱”的。当后台进程执行 `git reset --hard` 或类似的破坏性命令时，工作树中未提交的所有修改都会被无情地覆盖或删除。
*   **锁竞争**：多个进程同时操作 Git 仓库索引，导致了 `.git/index.lock` 冲突，使得我们的 Git 命令（如 `commit`、`status`）频繁失败。

## 3. 解决方案与成果固化

为解决此问题并防止其再次发生，我们采取了以下措施：

### 3.1. 紧急应对

1.  **进程识别**：尝试识别并终止后台运行的干扰性 `node.exe` 和 `git.exe` 进程。
2.  **立即提交**：在每次修改成功后，立即使用 `git commit --only <file>` 命令将更改固化到版本库中，使其脱离脆弱的工作树环境。这是本次会话中最重要的行动原则。

## 4. 预防策略与后续行动

为彻底杜绝此类问题，建议团队严格执行以下操作纪律：

### 4.1. 立即可执行的 Git 纪律

*   **“改完即存”**：任何原子性的代码或文档修改，完成后必须立即提交，**绝不能让未提交的修改在工作树中过夜**。
*   **隔离提交**：使用 `git commit --only <file>` 或 `git commit --only <file1> <file2>` 提交指定文件，物理上阻止其他无关的、可能是破坏性的修改被一起提交。
*   **警惕破坏性命令**：对 `git reset --hard`、`git checkout .`、`git clean -fd` 等命令保持高度警惕，执行前必须确认当前工作区状态，且**严禁在存在并发进程的环境下执行**。

### 4.2. 环境治理

*   **清理后台进程**：在开始新的开发会话前，应检查并终止可能在后台运行的、与项目相关的 `node.exe` 进程。特别是那些由 IDE 插件或临时脚本启动的进程。
*   **关闭非必要服务**：及时关闭调试用的开发服务器、文件监听器或自动化脚本，避免它们与 Git 操作产生竞争。
*   **使用隔离环境**：对于进行大改动或重构的任务，推荐使用独立的 `git worktree` 或在隔离的分支中进行，避免主线工作区受到干扰。

## 5. 总结

本次“工作树反复回退”事件深刻暴露了在并发环境下，未提交修改的脆弱性。通过立即提交关键修改、固化预防策略文档，我们不仅成功挽回了本次会话的成果，也为团队未来的开发工作建立了一套严格的 Git 操作纪律。

**核心教训：工作树不是可靠的存储介质，`git commit` 才是**。
