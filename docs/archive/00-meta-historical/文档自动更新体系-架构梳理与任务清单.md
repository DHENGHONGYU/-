## 一、体系现状架构梳理

### 1.1 资产盘点（10 个相关脚本 / 3 类角色）

| 脚本（npm 入口） | 真实能力 | 触发方式 | 是否接入 husky/CI | 读写范围 |
|---|---|---|---|---|
| `audit-doc-sync.ts`（`audit:docs`/`audit:docSync`） | 白盒审计：扫描 `src/` 变更，检查是否在 `docs/*.md`/DATA_DEFINITION/ARCHITECTURE/CHANGELOG/AGENTS 被引用 | **husky pre-commit 第7步 + lint-staged（docs/AGENTS/prompts）+ CI `quality-check.yml` P0 阻断门禁** | ✅ 已接入（仅审计） | 只读 + 报告 `docs/reports/audit/` |
| `doc-update-trigger.ts`（`doc:trigger`/`doc:check`） | 比对 `git diff` 与 8 条 `TRIGGER_RULES`（类型定义→数据字典 / 接口→API 契约 / Store→状态文档 / 页面→路由规格 …），**仅打印应更新文档的建议清单** | 手动 CLI | ❌ 未接入 | 只读；`--auto-update` 标注「尚未实现」 |
| `doc-auto-updater.ts`（`doc:auto-update`） | 编排器 v1：能力自动发现 → 基线版本检测(sha256+mtime) → git diff 比对 → 调 `syncCrossReferences`+`recordVersionHistory` 差异更新 → JSON+MD 双报告 | 手动 CLI（20/20 测试通过，成熟度 6.4/10） | ❌ 未接入 | `docs/*.md`/REGISTRY_INDEX/changelogs/报告 |
| `doc-freshness-score.ts`（`doc:freshness`） | 四维度加权评分（完整性30/时效25/准确25/一致20），输出 `docs/reports/doc-freshness/` | 手动 CLI（可被 updater 钩子调用但默认关） | ❌ 未接入 | 只写报告；`--auto-fix` 空桩未实现 |
| `daily-doc-validation.ts`（`daily-doc:validate`(:auto)） | 每日三维校验（完整性/一致性/正确性），`--auto-update` 时修断链+记版本 | 手动（头部注释宣称 GitHub Actions `cron 0 0 * * *`，**实际无任何 workflow 调用**，cron 跑的是 `system:check-loop`） | ❌ 未接入（含重试 `retryWithBackoff` maxRetries=3） | 同 updater |
| `doc-cross-ref-sync.ts`（`syncCrossReferences`） | 库：修 docs 相对断链 + 维护 `registry-index.md`（**全量重写**，非增量） | 被 updater/daily 导入 | 库依赖 | 写 docs |
| `doc-version-history.ts`（`recordVersionHistory`） | 库：追加每日变更到 `docs/changelogs/YYYY-MM/daily-doc-validation-*.md` | 被 updater/daily 导入 | 库依赖（承担版本联动落点） | 写 changelogs |
| `build-ai-memory-index.ts`（`build:ai-memory`） | 固定 `SOURCE_FILES` 切分 + 倒排索引 → `public/ai-memory-index.json` | 手动 | ❌ 未接入 | 生成工件 |
| `auto-fix-jsdoc.ts`（`auto:jsdoc`） | 读 jsdoc-audit 报告，向源码插占位 JSDoc | 手动 | ❌ 未接入 | 写 src（占位） |
| `inject-frontmatter.ts`（`inject:frontmatter`） | 批量向 `docs/implementation/*.md` 注入 YAML frontmatter（version 由 mtime 推断） | 手动（一次性） | ❌ 未接入 | 写 docs |

### 1.2 触发机制（用户关注点）

| 触发事件 | 当前真实行为 | 是否真正「更新文档」 |
|---|---|---|
| **代码提交（git commit）** | husky pre-commit 跑 `audit:docs`（第7步）+ lint-staged 对 docs/AGENTS/prompts 跑 `audit:docs` | ❌ 仅**审计/阻断**，不更新 |
| **PR 合并 / push** | CI `quality-check.yml` 将 `audit:docs` 设为 **P0 阻断门禁** | ❌ 仅**审计/阻断**，不更新 |
| **changelogs 变更（push/PR）** | CI `changelog-automation.yml` 校验 JSON → 生成月度报告 → **commit & push** | ✅ 唯一「生成→发布」自动流（范围窄） |
| **每日 cron** | CI `system-check-loop.yml` 跑 `system:check-loop`，**上传 `doc-freshness/*.json` 工件**（注：非 `daily-doc-validation`） | ❌ 仅产出评分工件，不更新 |
| **版本发布（release）** | **无任何触发器**；`package.json` version 2.0.0 与文档版本无自动绑定 | ❌ 缺失 |
| **手动 CLI** | 10 个脚本均可手动运行，但互不串联 | ⚠️ 依赖人肉串联 |

**结论**：自动化的只有「审计门禁」与「changelog 报告发布」两段；「代码变更 → 文档生成 → 校验 → 发布」的主链路**未闭合**，且**生成环节实质空缺**（`doc-update-trigger --auto-update` 与 `doc-freshness --auto-fix` 均为未实现空桩）。

### 1.3 更新范围覆盖度

| 文档类型 | 自动审计 | 自动更新 | 说明 |
|---|---|---|---|
| 数据字典 / 架构 / 路由 / 引擎规格 | ✅（audit:docs） | ❌ | 仅检测「未文档化文件」 |
| CHANGELOG | ⚠️（格式校验） | ✅（月度报告发布） | 仅 changelogs 子目录 |
| README / 索引 / 规范 | ✅（audit:docs） | ❌ | 无自动生成 |
| API 文档（api-extractor） | ⚠️（CI 生成 `../archive/api-report.md` 上传） | ✅（发布工件） | 非门禁、不回写 docs 树 |
| JSDoc（源码注释） | ✅（audit:jsdoc 基线） | ⚠️（`auto:jsdoc` 仅占位，手动） | 不写正文 |
| AI 记忆索引 | ❌ | ⚠️（手动 `build:ai-memory`） | 游离于自动流 |
| 文档交叉引用/断链 | ❌ | ⚠️（手动 updater） | 全量重写、非增量 |
| 文档版本历史 | — | ⚠️（手动 updater 调 recordVersionHistory） | 与代码无强绑定 |

### 1.4 自动化程度总评

- **已闭环自动**：审计（提交+PR 阻断）、changelog 报告生成发布。
- **半自动（手动触发但能力完整）**：`doc-auto-updater`（v1，文件级容错/双报告/版本检测已成熟）、`daily-doc-validation`（含重试）。
- **占位/未实现**：生成环节（`--auto-update`/`--auto-fix` 空桩）、daily cron 接线、版本与代码绑定、告警通知。
- **成熟度**：`doc-auto-updater` 6.4/10（B-，可用待加固）；`audit-doc-sync` 作为门禁已生产可用；整体体系**审计强、生成弱、编排断、无告警**。

## 三、完善优化：5 大约束落地（补全缺失环节）

针对 §二.4 的 5 类缺失，逐条给出**约束定义 + 落地方案 + 对应任务编号**。

### 约束 1：触发条件与更新动作需「一一映射」
- **现状缺口**：`doc-update-trigger` 的 8 条 `TRIGGER_RULES` 只打印建议，`--auto-update` 未实现；无强制映射表，更新动作与触发事件脱节。
- **落地方案**：新建 `docs/00-meta/doc-trigger-action-map.md`（单一事实源），定义 **触发事件 × 更新动作** 矩阵，每条触发事件精确对应 1 个（或 0 个，若无需更新）更新动作，杜绝「扫描全仓库」式误写。
  - 例：`类型定义变更(src/types/**)` → `更新对应数据字典条目 + 跑 audit:docs`
  - 例：`Widget 注册表变更` → `重写 cockpit DATA_DEFINITION + REGISTRY_INDEX(增量) + audit:docs`
  - 例：`package.json version bump` → `全仓文档 frontmatter version 同步 + CHANGELOG [Unreleased]→版本段`
- **对应任务**：T1（建映射表）、A1（限域，防越界）。

### 约束 2：更新失败需具备告警与重试机制
- **现状缺口**：仅 `daily-doc-validation` 有 `retryWithBackoff`(3)；`audit:docs` 靠非零退出阻断提交（无主动通知）；`doc-auto-updater` 无告警、无重试（仅文件级隔离）；`freshness-alerts` 规则定义但**从未激活**，无邮件/Slack/Issue 通知。
- **落地方案**：
  - **重试**：所有「写」类脚本统一封装 `retryWithBackoff`（指数退避，默认 maxRetries=3，仅对 `TRANSIENT/IO` 类错误重试，对 `FILE_NOT_FOUND/PARSE` 立即失败）。`doc-auto-updater` 接入（T2）。
  - **告警**：新增 `scripts/docs-tool/doc-update-trigger.ts`（适配器：CI 用 `::error`/Issue、本地用桌面通知/Webhook），在以下场景触发：①门禁非零退出 ②updater overallStatus=failure ③freshness 评分<50(ALERT-02) ④C1-C5 规则命中。错误分类学：`FILE_NOT_FOUND / PARSE / IO / TRANSIENT`（T3）。
- **对应任务**：A3（错误边界）、A7（退出码）、T2（重试）、T3（告警）、C1-C5（激活）。

### 约束 3：文档版本需与代码版本保持同步关联
- **现状缺口**：`package.json` version=2.0.0 与文档无自动绑定；`inject-frontmatter` 用 mtime 猜 version（弱）；`recordVersionHistory` 仅写 changelog，无 tag/版本号对照；无 release 触发器。
- **落地方案**：
  - 文档 frontmatter 新增 `code_version` 字段，CI 在 `version bump` 时校验与 `package.json` 一致（T4）。
  - `doc-version-history` 增加 `codeRef`：`{ gitTag, packageVersion, commitSha }`，每条文档变更关联代码版本（T5）。
  - release 流程（或 `npm version`）钩子：自动将 `[Unreleased]` 段提升为版本段 + 全仓 `code_version` 对齐（T6）。
- **对应任务**：T4/T5/T6、B12（版本比对常态化）。

### 约束 4：自动化流程需覆盖「生成→校验→发布」全链路
- **现状缺口**：生成环节为空桩；校验=audit:docs 已接入；发布=changelog 报告已接入；但三者未串成流水线，且 `doc-auto-updater`/`daily-doc-validation` 未接入 husky/CI。
- **落地方案**：建 `scripts/docs-tool/doc-sync-scheduler.ts`（或组合 npm 脚本），串联 `detect(trigger) → generate(映射动作) → validate(audit:docs+freshness) → publish(changelog/PR)`；在 CI 增加 `doc-automation.yml`（push/PR 触发），并把 `daily-doc-validation` 的真实每日 cron 接线（替换当前误接的 system-check-loop 或并行为独立 job）（T7）。
- **对应任务**：T7（端到端流水线）、A1-A6（updater 加固以安全接入）、B7/B14（PR 勾选+评审）。

### 约束 5：明确优先级排序及依赖关系，输出完整任务清单
- **现状缺口**：任务散落 3 处来源、无统一 owner/deadline、无依赖图。
- **落地方案**：本文 §四即统一任务清单（含 owner 建议 / 截止建议 / 依赖），并接入现有 `audit-path-match` 门禁使其可被持续发现（T8）；建议建立轻量看板（`docs/00-meta/doc-auto-update-kanban.md`）作为单一事实源。
- **对应任务**：T8（建看板）、全文 §四。
