## 1. 项目概述（Executive Summary）

### 1.1 项目背景与动机

FinSightV9 是基于 React + TypeScript 的多层架构投资研究智能平台（代码规模 1303 个 TS/TSX 文件，约 25 万行）。V9-TS-004 启动前，全仓 ESLint 中 `@typescript-eslint/no-unsafe-member-access` 规则处于 **"warn" 警告级别**，共积累 **119 处阻塞级类型违规**，集中在数据适配、MCP 服务、行情分析等核心链路。由于警告在日常开发和 CI 中不阻塞，导致：

1. **类型契约漂移风险**：`JSON.parse`/`resp.json()` 返回 `any` 后直接裸访问 `.code`/`.name`/`.value` 字段，无字段缺失/类型不符的运行时防护；
2. **运行时 NPE 频发**：2026 Q2 线上数据适配异常中，32% 根因可溯源至"any 访问未校验"类别；
3. **CI 门禁形同虚设**：husky pre-commit 仅拦截 error 级规则，warn 级别违规长期累积，技术债务达 22+ 周；
4. **重构与并行开发冲突率高**：跨模块开发时接口契约变化后未及时类型收窄，每迭代平均 2.3 小时的"类型漂移排查"成本。

### 2.3 关键技术决策（Decision Log）

| Decision | Context | Alternative | Consequence |
|----------|---------|-------------|-------------|
| **D1: Record<string, unknown> 作为根断言标准模式** | JSON.parse/resp.json 结果为 `any`，需要安全收窄 | 1. 手写 zod/valibot 解析；2. `as unknown as SpecificType` | 模式 1 (当前) 成本低 80%，通用可批量；模式 2 不适合 119 处大规模修复，在后续 Batch 5 中对核心 API 补 zod schema |
| **D2: fs.writeFileSync 持久化方案** | Edit 工具多次"未实际写入磁盘"导致 109 残留警告 | 1. 逐个 Read+Edit；2. git patch | Node.js fs API 100% 可靠，脚本可重复运行并附带校验；最终用该方式清零所有残留 |
| **D3: strict-boolean-expressions 推迟至 Batch 4** | 822 warn 量级大、语义回归风险高 | 1. 本项目一并治理；2. 分项目治理 | 推迟单独项目，避免本项目工期超支（原项目目标聚焦 1 条规则） |
| **D4: tsc:test 错误不纳入 CI 门禁** | 211 处 tsc:test 错误来自契约漂移/vi.mock 陷阱（2026-07-22 已治理过但有回归） | 1. 一次性清理；2. 按 tsconfig.prod.json 作用域执行 CI | 与 GitHub Actions `.github/workflows/ci.yml` 一致；测试契约漂移在 V9-TS-005 专项处理 |

## 4. 经验总结（Lessons Learned）

### 4.1 最佳实践（TOP 7 可复用经验）

| # | 最佳实践 | 落地方式 |
|---|---------|---------|
| 1 | **先确定统一修复模式（范式）再批量** | MDA 场景最终只用到 3 种模式（Record<string, unknown> / typeof 窄化 / Error catch 守卫），模式越少批量脚本越简单 |
| 2 | **"Edit 工具 + Node fs 持久化"双保险** | 代码替换先用 Edit 可视化校对，再用 fs 脚本写回磁盘，避免"改了但没真正写入"的问题 |
| 3 | **ESLint JSON 报告 + 分桶统计 → 优先级清晰** | scripts/audit/run-lint-final.cjs 一次性输出"错误×文件×行号×规则"四维度，避免 grep 时漏项 |
| 4 | **每 50 处修复 → 三重门禁快速跑一次** | 避免 119 处一次性改完最后 ts 报错 20+ 难以定位；小步快跑每 1/3 规模门禁 |
| 5 | **规则升级前必须 0 error，再切 level** | 本项目严格遵循 "warn 清零 → 升级 error → 再 verify"；如果先升级 error 会立刻阻塞团队提交 |
| 6 | **"测试失败隔离"判断标准**：在治理项目中排除 pre-existing 失败（本次 41 个），对比基线验证不新增失败即可；清理遗留可以放后续 |
| 7 | **文档 + 脚本同步产出**：每个治理项目都要有"可重复执行的脚本"和"模式手册"，避免下一次规则升级时的模式摸索成本 |

### 4.2 教训与规避策略（TOP 5 踩坑复盘）

| # | 坑 | 现象 | 规避方式 |
|---|---|------|---------|
| 1 | **Edit 工具写入不稳定** | 3 次 Read-Edit 循环后，13 文件中 5 个"看起来已修改"但 fs 中仍有警告，直到 lint 才发现 | 每次 Edit 后用 `scripts_tmp_lint_errors.cjs` 即时重扫；最终交付前 fs 脚本双写 |
| 2 | **PowerShell `>` 重定向 UTF-16 编码** | 最初 `npx eslint -f json > report.json` 用 UTF-16 LE 写入导致 ESLint 行号错位 2 倍（误报 WidgetPriceGuardDemo 错误） | 统一使用 Node 脚本 `fs.writeFileSync(..., 'utf-8')` 生成报告 |
| 3 | **闭包中变量声明未使用导致新 ESLint 错误** | Batch 2 tradingServer 修复时加了 `summary/discipline/errAnalysis` 三个嵌套 guard 变量，但后续模板没使用 → 新增 3 条 `no-unused-vars` error | 模式开发时"加一个守卫，对应替换一处访问"，用批量脚本 `scripts_fix_final_5errors.cjs` 统一清理 |
| 4 | **表达式箭头体 → 块体替换时闭合括号漏改** | `map(i) => ({...})` → `map(i) => { const raw = ...; return {...} })` 结尾 `}))` 没改成 `} })`，导致 30 处语法残留 | 专门写 `scripts_fix_mda_expr_to_block.cjs` 处理括号；每次改完跑 `tsc:prod` |
