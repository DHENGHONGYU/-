## 2. 修复策略

### 2.1 总体策略

**先易后难、分类推进、批量处理**：
1. **第一周**：批量修复低难度问题（Mock 不匹配、断言错误、简单 NaN 问题），快速降低失败数
2. **第二周**：集中攻克 NaN 传播问题和 Store 状态污染
3. **第三周**：处理异步/时序问题和排除文件
4. **第四周**：收尾 + 建立持续质量保障机制

### 2.2 修复原则

| 原则 | 说明 |
| :--- | :--- |
| **修代码优先于改测试** | 优先修复业务代码中的 bug，不轻易修改测试预期 |
| **保持测试意义** | 修复后测试仍应保持其原有的验证意图 |
| **最小变更** | 每个修复尽量聚焦，避免大范围重构 |
| **增量验证** | 每修复一批就跑全量测试，确认无回归 |
| **记录根因** | 每个失败都记录根因，归类到知识库 |

## 3. 分阶段执行计划

### 3.1 第一阶段：快速止损（第 1 周）— 目标：失败用例 ≤40

**重点**：批量处理低难度、高数量的问题

| 编号 | 任务 | 预计工时 | 预期减少失败 | 优先级 |
| :--- | :--- | :--- | :--- | :--- |
| W1-01 | NaN 返回值标准化（评分引擎） | 4h | ~15 用例 | P0 |
| W1-02 | Mock/Fixture 数据对齐 | 3h | ~10 用例 | P0 |
| W1-03 | 断言/类型错误修复 | 2h | ~5 用例 | P1 |
| W1-04 | test:known 中低难度文件修复 | 4h | ~8 用例 | P1 |
| W1-05 | 跳过用例分析与转化 | 1h | ~3 用例 | P2 |

**W1-01：NaN 返回值标准化**
- 根因：评分计算器在缺数据/行业不匹配时返回 NaN 而非 0
- 范围：`lMinus1.test.ts` 及其他评分计算相关测试
- 方案：在评分引擎入口增加 NaN 守卫，确保所有 score 字段返回有效数字
- 验证：修复后跑 `src/services/scoring/**/*.test.ts`

### 3.2 第二阶段：重点攻坚（第 2 周）— 目标：失败用例 ≤20

**重点**：Store 状态污染 + 复杂 NaN 传播

| 编号 | 任务 | 预计工时 | 预期减少失败 | 优先级 |
| :--- | :--- | :--- | :--- | :--- |
| W2-01 | Store 测试间状态隔离加固 | 6h | ~10 用例 | P0 |
| W2-02 | 复杂评分 NaN 传播链路修复 | 5h | ~10 用例 | P0 |
| W2-03 | DataBridge 测试稳定性 | 4h | ~5 用例 | P1 |
| W2-04 | test:known 中等难度文件 | 4h | ~5 用例 | P1 |

**W2-01：Store 状态隔离**
- 根因：部分测试间 Store 单例状态未完全重置
- 范围：所有使用 Zustand Store 的测试
- 方案：强化 `tests/setup.ts` 中的 beforeEach 重置逻辑，确保每个测试前 Store 回到初始状态
- 验证：连续运行全量测试 2 次，结果一致

## 4. 23 个缺测 Store 补齐计划

### 4.1 优先级分类

**P0（核心 Store，必须有测试）**：
- `researchPoolStore` — 研究池 Store
- `positionPoolStore` — 持仓池 Store
- `intentionPoolStore` — 意向池 Store
- `multiFactorScreeningStore` — 多因子筛选 Store
- `collectionWizardStore` — 采集向导 Store

**P1（重要 Store，应该有测试）**：
- `industryScoreStore` — 已有测试，需增强覆盖
- `intelligentScoreStore` — 已有测试，需增强覆盖
- `sevenDimConfigStore` — 七维配置 Store
- `runtimeTradingConfigStore` — 运行时交易配置 Store
- `dataSyncStore` — 数据同步 Store

**P2（一般 Store，可以后补）**：
- 其他约 13 个 Store

### 4.2 Store 测试模板

每个 Store 测试应覆盖：
1. **初始状态** — 验证初始 state 正确
2. **单个 Action** — 验证每个 action 的状态变更
3. **组合 Action** — 验证多个 action 组合的正确顺序
4. **边界情况** — 空数据、异常输入、大数量
5. **持久化** — 验证与 DataLayer 的交互
6. **订阅/通知** — 验证状态变更通知

## 5. 质量保障机制

### 5.1 测试门禁（Test Gate）

| 门禁项 | 当前值 | 目标值 | 检查频率 |
| :--- | :--- | :--- | :--- |
| test:clean 通过率 | 14/14 | 14/14 | 每次提交 |
| 全量测试通过率 | 97.8% | ≥99.5% | 每日构建 |
| 已知失败数 | 92 | ≤20 | 每周统计 |
| 排除文件数 | 8 | ≤3 | 每双周评审 |
| 覆盖率（core） | 55% | 70% | 每周统计 |
| 覆盖率（services） | 70% | 80% | 每周统计 |

### 5.2 持续改进机制

1. **每日测试报告**：CI 自动生成测试趋势图
2. **每周质量例会**：review 失败用例修复进度
3. **Flaky 测试追踪**：记录不稳定测试，纳入专项治理
4. **新代码测试要求**：PR 必须包含对应测试，覆盖率不下降

### 5.3 验证命令

```powershell
# 核心门禁（必须全绿）
npm run test:clean

# 全量测试（每日构建）
npm run test

# 已知问题集合（调试用）
npm run test:known

# 覆盖率检查
npm run coverage

# 测试审计（风格/质量）
npm run audit:tests
```

## 6. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
| :--- | :--- | :--- | :--- |
| NaN 问题涉及面广，修复周期长 | 进度延迟 1 周 | 中 | 先在引擎层统一加守卫，再逐层细化 |
| Store 状态污染根源复杂 | 修复成本高 | 中 | 引入测试专用重置工具函数，批量改造 |
| 异步时序问题难以复现 | 修复不确定 | 高 | 增加重试机制 + 更稳定的 Mock |
| 修复引入回归问题 | 质量风险 | 中 | 每批修复后跑全量测试验证 |
| 缺测 Store 工作量大 | 排期紧张 | 高 | 按优先级分批做，核心 Store 先覆盖 |
