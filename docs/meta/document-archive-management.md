## 一、文档生命周期模型

### 1.1 四阶段生命周期
```
草稿（Draft） → 活跃（Active） → 废弃（Deprecated） → 归档（Archived）
     ↓              ↓                ↓                    ↓
  编写中        正常维护         不推荐使用           停止维护
  不对外        持续更新         有替代文档           仅供查阅
```

## 二、死文档判定标准

### 2.1 判定维度

满足以下**任一**条件，可初步判定为死文档：
| 判定维度 | 具体条件 | 判定方式 | 权重 |
|----------|----------|----------|------|
| **功能失效** | 对应功能已从代码中移除 | 代码比对 | 决定性 |
| **版本过旧** | 超过 2 个大版本未更新 | 更新时间检查 | 重要 |
| **完全替代** | 有更新更完整的文档替代 | 内容比对 | 决定性 |
| **无引用** | 没有任何活跃文档引用它 | 引用扫描 | 重要 |
| **开发确认** | 领域负责人确认不再需要 | 人工确认 | 决定性 |
| **重复内容** | 与其他文档内容高度相似 (>80%) | 相似度检测 | 重要 |
| **临时文档** | 会议记录、临时方案、草稿 | 内容判断 | 参考 |
| **测试产物** | 测试报告、输出结果 | 内容判断 | 参考 |

### 2.2 初筛指标（自动化）
可通过脚本自动初筛的指标：

| 指标 | 阈值 | 说明 |
|------|------|------|
| 最后更新时间 | > 180 天 | 长时间未更新 |
| 被引用次数 | = 0 | 无任何文档引用 |
| 文档大小 | < 1 KB | 可能是空文档或占位符 |
| 状态标记 | `deprecated` | 已标记为废弃 |
| 目录位置 | `drafts/`、`temp/` | 草稿或临时目录 |

### 2.3 人工复核清单

初筛后的文档需要人工复核，检查：

- [ ] 文档描述的功能是否仍然存在？
- [ ] 是否有更新的替代文档？
- [ ] 内容是否与当前版本一致？
- [ ] 是否有人还在查阅使用？
- [ ] 是否有历史保留价值？
- [ ] 领域负责人是否确认可归档？
### 2.4 三审定级

| 审定级别 | 审核人 | 审核内容 |
|----------|--------|----------|
| 一审 | 文档管理员 | 初筛结果准确性 |
| 二审 | 领域负责人 | 功能相关性确认 |
| 终审 | 架构师 / 产品经理 | 最终裁定 |

## 三、审计流程
### 3.1 季度全量审计流程

```
第1周：初筛           第2周：复核           第3周：裁定        第4周：执行
  │                    │                    │                    │
  ▼                    ▼                    ▼                    ▼
脚本扫描          领域分组审核          终审会议           归档执行
生成清单          填写复核意见          形成终稿           移动+更新索引
```

### 3.2 月度快速审计

- 仅检查新增文档和上月修改的文档
- 快速识别明显的死文档
- 发现问题及时预警

### 3.3 审计产出

| 产出物 | 说明 | 格式 |
|--------|------|------|
| 死文档清单 | 待归档文档列表 | CSV + Markdown |
| 审计报告 | 审计过程和结论 | Markdown 报告 |
| 归档计划 | 归档执行时间表 | Markdown |
| 归档清单 | 已归档文档记录 | CSV + Markdown |

## 四、归档策略
### 4.1 归档分级

| 级别 | 名称 | 定义 | 保存位置 | 保留期限 |
|------|------|------|----------|----------|
| **A 级** | 重要历史 | 有重大参考价值的架构决策、里程碑文档 | `archive/important/` | 永久 |
| **B 级** | 普通历史 | 一般功能文档、旧版本文档 | `archive/normal/` | 2 年 |
| **C 级** | 草稿临时 | 草稿、临时记录、测试输出 | `archive/drafts/` | 6 个月 |

### 4.2 归档分级标准

**A 级（重要历史）**满足任一：
- 重大架构决策记录（ADR）
- 项目里程碑文档
- 核心算法设计文档
- 安全审计报告
- 架构师确认的重要文档

**B 级（普通历史）**满足任一：
- 已替代的功能文档
- 旧版本的规范文档
- 一般项目报告
- 领域负责人确认保留的

**C 级（草稿临时）**满足任一：
- 未完成的草稿
- 会议记录、临时方案
- 测试输出、自动生成
- 明显的临时文件

### 4.3 归档前准备

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 内容完整性检查 | 确保文档内容完整，不缺页 |
| 2 | Frontmatter 更新 | 添加归档状态、归档原因、归档日期 |
| 3 | **引用扫描与修复** | **强制步骤：扫描全仓引用，添加（已归档）注解或更新路径** |
| 4 | 清单登记 | 在归档清单中登记 |
| 5 | 备份 | 归档前做一次完整备份 |
| 6 | 审批 | 文档管理员审批确认 |

#### 步骤 3 引用扫描与修复（强制）

归档前**必须**执行全仓交叉引用审计，确保归档后不会产生断链：

```bash
# 1. 运行全仓审计，确认当前断链基线
npm run audit:doc-code-references

# 2. 归档文件后，再次运行审计
# 将所有新增的断链引用添加（已归档）注解或更新为替代文档路径
npm run audit:doc-code-references

# 3. 验证审计门禁通过（断裂率必须为 0.00%）
```

**修复策略**：

| 场景 | 操作 | 示例 |
|------|------|------|
| 归档文件有替代文档 | 更新引用路径为替代文档 | `<old-doc.md>` → `<new-doc.md>` |
| 归档文件无替代文档 | 在引用后添加 `（已归档）` 注解 | `` `<path/to/old.md>`（已归档）`` |
| 归档文件已完全废弃 | 在引用后添加 `（已废弃）` 注解 | `` `<path/to/old.md>`（已废弃）`` |

**检查清单**：
- [ ] 归档前运行 `npm run audit:doc-code-references`，记录基线
- [ ] 归档后再次运行审计，确认无新增断链
- [ ] 所有新断链引用已添加注解或更新路径
- [ ] 审计门禁 `断裂率 0.00%` 通过 |

### 4.4 归档执行

```bash
# 1. 更新文档 Frontmatter
status: archived
archived_date: YYYY-MM-DD
archive_reason: 原因说明
superseded_by: 替代文档路径（如有）

# 2. 移动到归档目录
# 保持原目录结构
archive/
  ├── important/
  │   └── reference/
  │       └── old-doc.md
  ├── normal/
  └── drafts/

# 3. 更新归档清单
# 在 archive/README.md 和 CSV 中登记

# 4. 清理原位置引用
# 更新所有指向该文档的链接
```

## 六、恢复与复用

### 6.1 恢复条件

归档文档可以在以下情况下恢复：
- 功能重新启用
- 需要参考历史实现
- 作为新版本的基础
- 审计或合规要求
### 6.2 恢复流程

| 步骤 | 操作 | 审批人 |
|------|------|--------|
| 1 | 提出恢复申请，说明原因 | 申请人 |
| 2 | 确认恢复后用途和维护计划 | 领域负责人 |
| 3 | 文档管理员审批 | 文档管理员 |
| 4 | 执行恢复（移回原位置 + 更新状态） | 文档管理员 |
| 5 | 更新清单和索引 | 文档管理员 |
| 6 | 内容更新（如需要） | 领域负责人 |

### 6.3 复用指南

**直接复用**：
- 内容仍然适用 → 恢复后直接使用
- 需要小修改 → 恢复后更新版本号

**参考复用**：
- 作为新项目/新功能的参考
- 不恢复原文档，在新文档中引用
- 保持原文档归档状态

### 7.3 定期审计机制（已建立）

#### 7.3.1 审计脚本

| 脚本 | 用途 | 执行频率 |
|------|------|----------|
| `scripts/audit/audit-dead-docs.ps1` | 死文档全量扫描（8类检测） | 季度 |
| `scripts/audit/audit-quarterly-doc-health.ps1` | 季度文档健康度（断链/过期/元数据） | 季度 |
| `scripts/audit/audit-doc-health-orchestrator.ps1` | 统一编排器（串联上述所有检查） | 月度/季度 |

#### 7.3.2 NPM Scripts

| 命令 | 说明 |
|------|------|
| `npm run audit:dead-docs` | 死文档审计（Dry Run） |
| `npm run audit:dead-docs:execute` | 死文档审计（执行归档） |
| `npm run audit:quarterly-doc-health` | 季度文档健康度审计 |
| `npm run audit:doc-health` | 全量文档健康度审计（full 模式） |
| `npm run audit:doc-health:monthly` | 月度快速审计（跳过死文档扫描） |
| `npm run audit:doc-health:quarterly` | 季度全量审计（含死文档扫描） |

#### 7.3.3 调度任务

| 任务 | 调度 | 首次执行 |
|------|------|----------|
| 月度文档死文档审计 | 每月1日 09:00 (Asia/Shanghai) | 2026-09-01 |
| 季度全量文档健康度审计 | 1/4/7/10月1日 10:00 (Asia/Shanghai) | 2026-10-01 |

#### 7.3.4 Pre-commit 门禁提醒

每次 `git commit` 时，pre-commit hook 会自动检查：
- 月初（1号）提醒执行月度审计
- 季度首月（1/4/7/10月）提醒执行季度审计
- 距上次审计超过30天提醒补充审计

#### 7.3.5 审计报告位置

所有审计报告输出到 `docs/reports/audit/`：
- `doc-health-orchestrator-{date}.md` — 综合编排报告
- `doc-health-orchestrator-{date}.json` — 结构化数据（支持趋势对比）
- `dead-docs-audit-{date}.md` — 死文档详细报告
- `dead-docs-audit-{date}.csv` — 死文档清单（CSV）
- `quarterly-doc-health-{date}.md` — 季度健康度详细报告
- `quarterly-doc-health-{date}.json` — 健康度结构化数据
