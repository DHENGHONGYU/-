## 〇、摘要（Executive Summary）

本次梳理对 V9 项目的文档资产做了全量检索与深度解读，核心结论如下：

1. **文档体量庞大但导航缺失**：`docs/` 下 1794 个文件，其中约 1401 个（78%）为 `reports/` 自动生成产物（JSON/HTML），叙事型核心文档分散在 `02-design/`（140）、`01-requirements/`（42）、`audit/`（43）等目录。**缺少统一的 `docs/README.md` 顶层索引**。
2. **架构权威文档存在命名误导**：整体架构与分层约束实际沉淀在根级 `../../AGENTS.md`（AI 行为约束契约），而根级 `../explanation/03-architecture-standards.md` 实为「驾驶舱 Widget 子系统架构」，并非 V9 全局架构说明。
3. **组件 / 状态 / 服务 / Widget 注册表多为代码层**：`componentRegistry.ts`、`widgetRegistry.ts`、`withBroadcast.ts`、`dataSourceRegistry.ts` 是代码层"注册表"，对应集成规范散落在 `prompts/` 模板与各 checklist，未沉淀为统一集成规范文档。
4. **5 舱体系文档不完整**：仅 `input` 舱有独立 spec（input-cabin-spec.md），`analysis / trading / output / command` 四舱缺独立规格文档。
5. **文档漂移（doc-drift）已发生**：`../explanation/design/00-readme.md` 标注 `docs/implementation/` 有 44 份文档，实际 `implementation/` 仅 14 份；该索引文件自身位于 `02-design/` 而非其声称的 `implementation/`。

基于此，本文提出一套 **8 大类（A–H）文档归类体系**，覆盖架构设计、功能模块、技术规范、测试策略等维度，并为每类给出「说明 / 适用范围 / 现有文档映射 / 缺口与建议」。

## 一、方法论与依据

### 1.1 检索与解读方法

| 步骤 | 做法 | 产出 |
|------|------|------|
| 文档检索 | 全量遍历 `docs/` 子目录、根级 `.md`、根级配置文件、`prompts/`，按 13 个主题维度归类 | 文档清单（见附录 A） |
| 深度解读 | 精读 `../../AGENTS.md`、`../explanation/03-architecture-standards.md`、`../README.md`、`../explanation/design`、`../how-to/testing/testing-strategy.md`、`../explanation`、`../README.md` 等枢纽文档 | 每类内容定位与核心要点 |
| 策略对照 | 以业界框架（Diátaxis、arc42、ADR、Test Pyramid、Quality Gates、Design System、Docs-as-Code）为标尺 | 缺口清单（见第三章） |
| 体系构建 | 合并"现有文档映射 + 缺口"为分层分类树 | 本文档第四章 |

### 1.2 业界参照框架（用于查漏补弃）

- **Diátaxis**（文档四型）：Tutorials（教程）/ How-to Guides（操作指南）/ Reference（参考）/ Explanation（原理阐述）。
- **arc42**（架构文档模板）：上下文、约束、解决方案策略、构建块、运行时、部署、跨切、架构决策。
- **ADR**（架构决策记录，<https://adr.github.io>）：轻量、不可变、带编号的决策记录。
- **测试金字塔 / 质量门禁**：单元 > 集成 > E2E 的分层投入；pre-commit / CI / release 三级门禁。
- **Design System / 设计令牌**：原子化组件 + 分层设计令牌（参考 Atomic Design、shadcn/ui、Ant Design）。
- **Docs-as-Code**：文档与代码同仓、同 PR、同审计、Frontmatter 元数据、保鲜度告警。

> **【适用范围】** 哪些角色/场景应消费此类文档；
